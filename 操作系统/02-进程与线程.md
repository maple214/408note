## 一、本章知识框架

- **（一）进程与线程**
  - 进程的基本概念
    - 定义：进程是进程实体的**运行过程**，是系统进行**资源分配**和**独立调度**的基本单位
    - 五大特征：动态性（最基本）、并发性、独立性、异步性、结构性
    - 进程实体（进程映像）= **程序段 + 数据段 + `PCB`**
    - `PCB`：操作系统感知进程存在的**唯一标志**；进程存在的全部信息都在里面
    - 进程 ≠ 程序：程序静态、进程动态；一程序可对应多进程，一进程可执行多程序
  - 进程的状态与转换
    - 三态：就绪、运行、阻塞
    - 五态：新建、就绪、运行、阻塞、终止
    - 七态：再加**就绪挂起、阻塞挂起**（与中级调度、对换区挂钩）
    - **不可能发生的转换**：阻塞 → 运行、就绪 → 阻塞（考点集中在这里）
  - 进程的组织与控制
    - 组织：链接方式、索引方式（多个就绪/阻塞队列）
    - 控制：都用**原语**（原子操作）；创建、终止、阻塞与唤醒、切换
    - 阻塞是**进程自身**的主动行为（`block`），唤醒是**别的进程**的被动施救（`wakeup`）
  - 线程
    - 引入动机：进程当"资源拥有者"太重，切换与创建开销大、并发度受限
    - 线程是**调度与分派**的基本单位，本身**不拥有**系统资源，只独享少量运行必需资源
    - 实现方式：用户级线程 `ULT`、内核级线程 `KLT`、组合方式
    - 三种多线程模型：多对一、一对一、多对多
  - 进程间通信 `IPC`
    - 共享内存（最快，但要自己做同步互斥）
    - 消息传递（直接通信 / 间接通信＝信箱、消息队列）
    - 管道（半双工、匿名管道 vs 命名管道、容量与阻塞规则）
    - 信号（`signal`，传"事件通知"而不是传数据）
- **（二）`CPU` 调度与上下文切换**
  - 三级调度：高级调度（作业调度）、中级调度（内存调度）、低级调度（进程调度）
  - 调度时机：何时能调、何时**不能**调；非抢占式 vs 抢占式
  - 调度程序 + **闲逛进程**（`idle`，让 `CPU` 永不空闲）
  - 六个评价指标：`CPU` 利用率、系统吞吐量、周转时间、带权周转时间、等待时间、响应时间
  - 调度算法（七个）：`FCFS`、`SJF`/`SPF`（非抢占）、`SRTN`（抢占）、`HRRN`、`RR`、优先级、多级队列、多级反馈队列 `MLFQ`
  - 多处理机调度：处理器亲和性、负载均衡
  - 上下文切换：切了什么、开销从哪来、内核级/用户级线程调度的差别
- **（三）同步与互斥**
  - 临界资源、临界区、同步（直接制约）与互斥（间接制约）
  - 访问临界区四原则：空闲让进、忙则等待、有限等待、**让权等待**
  - 软件方法：单标志法、双标志先检查、双标志后检查、`Peterson` 算法
  - 硬件方法：中断屏蔽、`TestAndSet`、`Swap`
  - 锁：自旋锁（忙等待）vs 互斥锁（阻塞等待）
  - 信号量：整型 / 记录型；`P`（`wait`）/ `V`（`signal`）；互斥、同步、前驱关系三种用法
  - 条件变量（大纲未单列，了解即可）
  - 经典同步问题：生产者-消费者、多生产者-多消费者、读者-写者、哲学家进餐

  - 定义与四个必要条件：互斥、不可剥夺、请求并保持、循环等待
  - 与饥饿、死循环的区别；四种处理策略（鸵鸟、预防、避免、检测解除）

## 二、概念详解

### 2.1 进程与线程的基本概念

#### 2.1.1 为什么会有"进程"

早期的**单道批处理系统**一次只放一道程序进内存，程序运行时 `CPU` 等 `I/O`、`I/O` 等 `CPU`，机器大量时间在空转。**多道批处理系统**让多道程序同时驻留内存交替执行，于是出现两个新问题：

1. 内存里同时有好几道程序，**怎么区分它们**、各自用到哪些资源？
2. 一道程序被暂停、另一道接着跑，**现场（寄存器、`PC`）保存在哪**？

"程序"这个概念答不了这两个问题——程序是静态的、没有"现场"。于是引入**进程**：它既能标识"是哪一道程序在执行"，又能装下"执行到哪儿了、占了哪些资源"。

**进程的定义**：进程是进程实体的**运行过程**，是系统进行**资源分配**和**独立调度**的基本单位。

**进程实体（进程映像）= 程序段 + 数据段 + `PCB`**。所谓"创建进程"，本质就是**创建 `PCB`**；所谓"撤销进程"，本质就是**撤销 `PCB`**。

**五大特征**：

| 特征 | 含义 | 记忆抓手 |
| --- | --- | --- |
| 动态性 | 进程是程序的一次执行过程，有创建、活动、暂停、终止的**生命周期** | **最基本**的特征，是"进程"区别于"程序"的根本 |
| 并发性 | 多个进程实体同存于内存，能在一段时间内**同时运行**（宏观同时、微观交替） | 引入进程的**目的**就是支持并发 |
| 独立性 | 进程是能**独立运行、独立分配资源、独立接受调度**的基本单位 | 未建立 `PCB` 的程序不能独立运行 |
| 异步性 | 各进程按**各自独立的、不可预知的速度**向前推进 | 所以必须配合同步机制 |
| 结构性 | 每个进程都配置一个 `PCB` 及其结构 | 指的就是程序段+数据段+`PCB` |

**进程与程序的对比**：

| 对比项 | 程序 | 进程 |
| --- | --- | --- |
| 性质 | **静态**的指令集合 | **动态**的执行过程 |
| 存在时间 | 可长期保存（存于磁盘） | 有生命周期，暂时存在 |
| 数量关系 | 一个程序可对应多个进程 | 一个进程也可执行多个程序（如 `C` 程序调用多个函数，或分阶段执行不同程序） |
| 组成 | 指令 + 数据 | 程序段 + 数据段 + `PCB` |
| 并发性 | 单程序无法并发 | 是并发的基本单位 |

**`PCB`（进程控制块）的内容与作用**

内容大致四类：

- **进程标识符**：内部 `PID`、外部标识（创建者、用户）
- **处理机状态（现场信息）**：通用寄存器值、指令计数器 `PC`、程序状态字 `PSW`、用户栈指针——**切换进程时必须保存/恢复的就是这一块**
- **进程调度信息**：进程状态、优先级、调度所需的其他信息、事件（阻塞原因）
- **进程控制信息**：程序与数据的地址、资源清单、同步与通信机制、链接指针

作用一句话：**`PCB` 是进程存在的唯一标志**，是操作系统管理进程的"档案"；分配资源实质上是把资源登记到该进程的 `PCB` 上。

> **408 怎么考 / 常见坑**
>
> - 常考"进程存在的唯一标志是 `PCB`"，不要选"程序段"或"数据段"。
> - "进程是资源分配的基本单位"与"线程是调度的基本单位"这一组说法要能对调问、反向问。
> - 陷阱项："进程是程序的一次执行，因此一个程序只能对应一个进程"——错（同一程序可被多个用户多次启动）。
> - 陷阱项："进程具有静态性"——错，只有程序静态。
> - "动态性是最基本的特征"是标准答案；"并发性"是引入进程的目的，别混淆。

#### 2.1.2 进程的状态与转换

**为什么需要状态**

进程在生命周期里并不是一直"在 `CPU` 上跑"。它可能在等 `CPU`、可能被调度上去跑、可能在等 `I/O` 完成、可能刚被创建或即将被销毁。给这些处境分类，操作系统才能知道"该把 `CPU` 发给谁"。

**（1）三种基本状态**

- **运行态**：占有 `CPU`，正在 `CPU` 上执行。**单处理机中任一时刻最多一个**。
- **就绪态**：已具备运行条件（资源都齐了），只差 `CPU`。就绪进程排成就绪队列。
- **阻塞态（等待态）**：因等待某事件（`I/O` 完成、申请资源失败、`P` 操作不成功）而**暂停**执行，即使给 `CPU` 也跑不动。

**（2）五态模型**：在就绪前加"新建态"（`PCB` 已建、资源未齐），在运行后加"终止态"（已结束、资源待回收）。

**（3）七态模型**：为支持**中级调度（对换）**，把不能运行的进程换到外存，于是多出：

- **就绪挂起**：进程在外存，但一旦调入内存就可运行
- **阻塞挂起**：进程在外存，且仍在等待某事件

**状态转换图（文字版，务必能自己画出来）**

```text
                 创建              调度（低级调度）
  新建 ──────────────► 就绪 ──────────────────────► 运行 ──────► 终止
                        ▲  │                          │
               事件发生  │  │ 时间片用完 / 被抢占       │ 等待事件
             （唤醒）    │  ◄──────────────────────────┤ （请求 I/O、P 操作失败）
                        │                             ▼
                        └──────────── 阻塞 ◄───────────┘
                              （阻塞的过程本身就是"运行 → 阻塞"）

  内存 ◄──── 挂起/激活 ────► 外存
  就绪 ⇄ 就绪挂起    阻塞 ⇄ 阻塞挂起
```

**四种基本转换及其原因**：

| 转换 | 原因 | 谁发起 |
| --- | --- | --- |
| 就绪 → 运行 | 被调度程序选中 | 操作系统（调度） |
| 运行 → 就绪 | 时间片用完 / 被更高优先级进程抢占 | 操作系统（时钟中断、抢占） |
| 运行 → 阻塞 | 主动请求某事件（`I/O`、资源、`P` 操作）而无法立即满足 | **进程自身**（主动） |
| 阻塞 → 就绪 | 等待的事件发生了 | **别的进程**（如 `I/O` 完成中断、`V` 操作唤醒） |

**明确不可能发生的转换**（选择题高发区）：

- **阻塞 → 运行**：不可能，必须先回到就绪队列排队。
- **就绪 → 阻塞**：不可能，就绪进程没有在 `CPU` 上执行，谈不上"请求事件而阻塞"。
- 运行 → 阻塞是**一步**完成的：一个正在运行的进程请求 `I/O`，直接进入阻塞态，中间不经过就绪态。
- 挂起态的进程**不能被调度**（不在内存）；就绪挂起需先"激活"成就绪态。

> **408 怎么考 / 常见坑**
>
> - 最爱考"下列状态转换中不可能的是"，答案通常是"阻塞 → 运行"或"就绪 → 阻塞"。
> - "阻塞→就绪"与"运行→阻塞"是**不同进程**在配合：A 阻塞时 B 在运行，B 后来唤醒 A。答题时若说"A 自己把自己唤醒了"就错了。
> - 单处理机上"运行态进程有多个"必错；阻塞态进程可以有多个（数量不受限）。
> - 挂起状态属于**七态**模型，涉及"进程被换出到外存"；只有内存中的进程才能被调度，这句要能接住选择题。

#### 2.1.3 进程的组织与控制

**组织方式**

- **链接方式**：按状态把 `PCB` 链成多个队列（就绪队列、若干阻塞队列）。就绪队列按优先级排序，指针指向队首。
- **索引方式**：为每种状态建一张索引表，表项指向对应 `PCB`。现代系统多用索引 + 队列的组合（如 Linux 的就绪队列用红黑树/RunQueue，阻塞用等待队列）。

**进程控制 = 用原语完成**

**原语**是由若干指令构成的、**执行期间不可被中断**的原子操作，靠**关中断/开中断**实现。为什么必须原子？因为进程控制的每一步都在改 `PCB` 和队列，若中途被打断，队列就会不一致。

| 原语 | 干什么 | 关键点 |
| --- | --- | --- |
| 创建 | 分配 `PCB`（申请空白 `PCB`、填信息、分配 `PID`）→ 分配资源 → 初始化 `PCB` → 插入就绪队列 | **先有 `PCB` 才有进程**；资源不足则进就绪挂起队列 |
| 终止 | 找到 `PCB` → 若在运行则剥夺 `CPU` → 终止其所有子进程 → 归还资源给父进程或系统 → 移出队列 | 必须处理"子进程"与"资源归还对象" |
| 阻塞 | 保存现场 → 改状态为阻塞 → 插入对应事件的阻塞队列 → 转调度程序 | **主动行为**，由本进程调用 `block` |
| 唤醒 | 从阻塞队列摘出 `PCB` → 改状态为就绪 → 插入就绪队列 | **被动行为**，由其他进程调用 `wakeup`；被唤醒进程不能立即运行 |
| 切换 | 保存当前进程现场到其 `PCB` → 恢复新进程现场 → 更新 `PCB` 与队列 | 切换在**内核**完成，开销落在这里 |

**原语成对出现**：`block` 与 `wakeup`、创建与终止，都把"改状态"和"进出队列"捆绑在一起做。

> **408 怎么考 / 常见坑**
>
> - "进程创建时首先做什么"——**申请空白 `PCB`**。
> - "阻塞是主动的、唤醒是被动的"是判断改错题的钥匙：被唤醒的进程**不会立刻获得 `CPU`**，只是回到就绪队列。
> - 原语不可中断靠**关中断**实现，注意与"中断屏蔽方法实现互斥"是同一思想但不同场合。

#### 2.1.4 线程

**为什么引入线程**

进程既是"资源拥有者"又是"调度单位"，两个角色捆在一起带来三个问题：

1. **创建/撤销/切换开销大**：进程切换要换页表、刷 `TLB`、换地址空间。
2. **并发度受限**：一个进程同一时刻只能做一件事；要同时干多件事就得开多个进程，而进程间共享数据又很麻烦。
3. **通信开销大**：进程间通信必须经过内核。

于是把两个角色拆开：**进程只当资源拥有者，线程当调度与分派的基本单位**。同一进程内的线程共享该进程的地址空间与资源（代码段、数据段、打开的文件），因此切换时不用换地址空间，开销小得多。

**线程独享的东西（易错点）**：线程 `ID`、程序计数器 `PC`、寄存器组、栈（含栈指针）。**共享的东西**：地址空间（代码段、数据段、堆）、打开的文件、信号处理方式等。

**进程与线程对比表**

| 对比项 | 进程 | 线程 |
| --- | --- | --- |
| 基本单位 | **资源分配**的基本单位 | **调度/分派**的基本单位 |
| 拥有资源 | 拥有独立地址空间和资源 | 基本不拥有资源，共享所属进程的资源 |
| 并发性 | 进程之间可并发 | 同进程内线程也可并发，并发度更高、切换更快 |
| 地址空间 | 各自独立，切换要换页表（开销大） | 同一进程内共享，切换不换地址空间（开销小） |
| 系统开销 | 创建、撤销、切换都大 | 小得多（但仍需保存 `PC`、寄存器、栈） |
| 通信 | 需要 `IPC` 机制，经内核 | 直接读写共享变量，快，但**必须自己做同步互斥** |
| 独立性 | 一个进程崩溃一般不影响别的进程 | 一个线程崩溃可能拖垮同进程的**所有线程** |

**线程的实现方式**

- **用户级线程 `ULT`**：由**线程库**在用户空间实现，操作系统内核**看不见**线程，只看到它所属的那个进程。
  - 优点：线程切换不需陷入内核（在用户态完成），开销小、速度快；可在不支持线程的操作系统上实现。
  - 缺点：一个线程执行**阻塞系统调用**，内核会阻塞**整个进程**；**不能利用多核**（内核只把 `CPU` 分给进程）。
- **内核级线程 `KLT`**：由操作系统内核支持和管理，`TCB` 在内核。
  - 优点：一个线程阻塞不影响同进程其他线程；多处理机上可**真正并行**。
  - 缺点：线程切换要进内核（用户态↔内核态），开销较大。
- **组合方式**：用户级线程 + 内核级线程建立多对多映射。

**三种多线程模型**

| 模型 | 映射关系 | 特点 |
| --- | --- | --- |
| 多对一 | 多个用户级线程 → 1 个内核级线程 | 切换快；一个阻塞全阻塞；**不能并行**（不能利用多核） |
| 一对一 | 1 个用户级线程 → 1 个内核级线程 | 并发性最好；每开一个线程就要一个内核线程，开销大，线程数受限 |
| 多对多 | `n` 个用户级线程 → `m` 个内核级线程（`n >= m`） | 兼顾开销与并发；实现最复杂 |

> **408 怎么考 / 常见坑**
>
> - "用户级线程的切换不需要操作系统干预"——对；"用户级线程的调度由内核完成"——错。
> - **关键陷阱**："用户级线程切换比内核级线程快，所以线程切换一定比进程切换开销小"——前半句对，后半句要看实现层级。**同进程内内核级线程之间的切换，其开销与进程切换相当（都要陷入内核、保存现场）**，而用户级线程间切换才真正便宜。王道这里反复设坑。
> - 常考"一个线程阻塞是否导致整个进程阻塞"：用户级线程**会**，内核级线程**不会**。
> - 常考"用多线程能否提高并行度"：用户级线程在多处理机上**不能**真正并行。

#### 2.1.5 进程间通信

进程有独立地址空间，一个进程不能直接访问另一个进程的变量，所以要 `IPC` 机制。三条思路：**共享一块区域**（共享内存）、**让内核帮忙搬数据**（消息传递/管道）、**只发通知不发数据**（信号）。

| 方式 | 怎么用 | 优点 | 缺点 / 坑 |
| --- | --- | --- | --- |
| 共享内存 | 内核在内存中划出共享区并映射到双方地址空间，双方直接读写 | **速度最快**（无需内核介入搬运） | 必须**自己做同步互斥**；共享区的建立/映射仍需系统调用 |
| 消息传递 | 用 `send` / `receive` 两个原语交换**格式化的消息** | 无需共享地址空间，适合分布式 | 每次都要陷入内核，数据要拷贝 |
| 管道 `pipe` | 一个**共享文件**（内存中的缓冲区），以字符流写读 | 使用简单，自带同步（满则写阻塞、空则读阻塞） | 半双工、数据无格式、多数实现是**字节流** |
| 信号 `signal` | 内核向进程发送一个信号编号 | 轻量、异步 | **只传"发生了什么事"，不传数据** |

**消息传递的两种方式**

- **直接通信**：`send(接收进程, 消息)` / `receive(发送进程, 消息)`，原语上直接写对方 `PID`。一对一的链路，发送方与接收方要"点名"。
- **间接通信**：消息发到**信箱/消息队列**（`mailbox`），`send(信箱, 消息)` / `receive(信箱, 消息)`。解耦，支持多发送者/多接收者，是更常用的形式。

**管道**

- **半双工**：同一时刻数据只能单向流动；要双向通信需两条管道。
- **匿名管道**：`pipe()` 创建，只存在于内存，**只能用于有血缘关系（父子/兄弟）的进程**，进程退出即消失。
- **命名管道 `FIFO`**：有文件名、在文件系统中可见，**任意进程**都可通过路径打开，与血缘无关。
- **同步特性**：管道是**固定大小的循环缓冲区**。写进程在**管道满**时阻塞，读进程在**管道空**时阻塞；读走数据后写进程被唤醒。写端全部关闭后读进程读到的 `read` 返回 `0`（`EOF`）。
- 要点：管道提供的是**字节流**，没有消息边界；数据一旦被读走就消失，不能重复读。

> **408 怎么考 / 常见坑**
>
> - 常考"共享内存与其他 `IPC` 相比，优势是**速度快**，但**需要用户自己实现同步**"。
> - 常考"管道是**半双工**的""匿名管道只能用于**有血缘关系**的进程""管道满时写进程阻塞、空时读进程阻塞"。
> - 陷阱项："信号传递的是数据"——错，信号只传事件通知；数据要靠共享内存、消息、管道。
> - 陷阱项："共享内存由内核负责同步"——错，内核只负责建立映射。
> - 陷阱项："用管道通信时数据可以由读进程读取多次"——错，读完即消失。

### 2.2 `CPU` 调度与上下文切换

#### 2.2.1 调度的基本概念与三级调度

**为什么需要调度**：进程数远多于 `CPU` 数（常常是 1 个），必须决定"此刻 `CPU` 给谁"，以在吞吐量与响应速度之间取得平衡。

**三级调度**

| 层次 | 别名 | 干什么 | 频率 | 是否有它 |
| --- | --- | --- | --- | --- |
| 高级调度 | 作业调度 / 长程调度 | 从**外存后备队列**中选作业调入内存，为其创建进程 | 最低（分钟级） | 批处理系统有；分时/实时系统常无 |
| 中级调度 | 内存调度 / 中程调度 | 决定哪些进程可留在内存、哪些**换出到外存**（挂起/激活） | 中等 | 引入虚拟内存后才有 |
| 低级调度 | 进程调度 / 短程调度 | 从**就绪队列**选一个进程分配 `CPU` | 最高（毫秒级，最频繁） | **所有操作系统都必备** |

**调度时机（什么时候会触发调度）**

- 进程**正常终止**或异常终止
- 进程**主动阻塞**（请求 `I/O`、`P` 操作失败）
- 进程被**唤醒**（回到就绪队列）
- **时间片用完**（时钟中断）
- 有**更高优先级**进程到达或被唤醒（仅抢占式）
- 中断处理结束、系统调用返回用户态时（很多系统的集中调度点）

**不能进行进程调度的情况**（考选择题）

- **中断处理过程中**（中断处理是内核的关键工作，不允许切换）
- 进程**在操作系统内核临界区中**（访问共享数据结构，切换会破坏一致性）
- **原子操作**（原语）执行期间
- 内核的不可中断代码段（如加锁的自旋区）内

**非抢占式 vs 抢占式**

| 对比项 | 非抢占式（非剥夺） | 抢占式（剥夺） |
| --- | --- | --- |
| 何时切换 | 只有进程**主动放弃** `CPU`（终止、阻塞）才切换 | 只要出现更紧急的情况就可**强行剥夺** |
| 具体触发 | 运行结束、阻塞 | 时间片用完、更高优先级到达、更短作业到达 |
| 优点 | 实现简单、开销小；对内核数据结构友好 | 响应快、能保证实时性、能实现公平 |
| 缺点 | 长作业/低优先级可能长期占用；不适合分时与实时 | 切换频繁、开销大；要处理并发访问共享数据的临界区问题 |
| 代价 | 周转时间可能很差 | 调度开销 + 需保护临界区 |

**闲逛进程（`idle`）**

系统**故意**设置一个优先级最低的进程（Linux 中为 `PID 0` 的 `swapper`）。当就绪队列为空时调度它运行。作用：

- 保证 `CPU` **任何时候都有活干**，不会出现"无事可做却要反复判断"的空转；
- 它是**唯一可以被随时剥夺**的进程；
- 闲逛进程**不消耗 `CPU` 时间**（执行 `halt`/`WFI` 让 `CPU` 进入低功耗状态），一旦有别的就绪进程立即被换下。

#### 2.2.2 调度目标与评价指标

**调度目标**（互相矛盾，需权衡）：`CPU` 利用率高、系统吞吐量大、周转时间短、等待时间短、响应时间快、公平、优先满足紧急任务。

**六个指标**（务必会算）

设某作业到达时间为 `arrival`，开始时间为 `start`，完成时间为 `finish`，实际运行时间为 `service`（服务时间），

- **`CPU` 利用率** = `CPU` 有效工作时间 / 总时间`。`
- **系统吞吐量** = `单位时间内完成的作业数`。
- **周转时间** = `作业完成时间 - 作业到达时间` = `finish - arrival`。它包含**等待时间 + 运行时间 + 被抢占/换出的时间**。
- **带权周转时间** = `周转时间 / 运行时间`（`= 1 + 等待时间 / 运行时间`）。**恒 >= 1**，等于 1 表示一到达就跑、跑完就结束。
- **平均周转时间** = `所有作业周转时间之和 / 作业数`。
- **平均带权周转时间** = `所有作业带权周转时间之和 / 作业数`。
- **等待时间** = `周转时间 - 运行时间 - I/O 时间`（只算在就绪队列里干等的时间；被 `I/O` 阻塞的时间不算等待）。
- **响应时间** = `首次提交请求到首次得到响应的时间`，分时系统最关心。

> **408 怎么考 / 常见坑**
>
> - 大题几乎固定要求：画调度顺序 → 列每行"到达/运行/开始/完成/周转/带权"表格 → 求平均。
> - **带权周转时间恒 >= 1**，若算出小于 1 一定是算错（把等待时间当成周转时间了）。
> - 有些题给的是"作业提交时间"和"估计运行时间"，那就用 `finish - submit` 和 `周转 / 运行`。
> - 注意区分"等待时间"与"被 `I/O` 阻塞时间"：王道题常给 `I/O` 时间，等待时间要把它扣掉。

#### 2.2.3 `CPU` 调度算法

**（1）先来先服务 `FCFS`**

- **思想**：按进入就绪队列（或作业到达后备队列）的先后顺序服务。
- **抢占性**：**非抢占**。
- **优点**：实现最简单、公平（对先到者）；不会饥饿。
- **缺点**：对**短作业不利**（若长作业先到，后面短作业的带权周转时间会爆炸）；对 `I/O` 繁忙型作业不利（`CPU` 繁忙型作业一直占着 `CPU`）。
- **适用**：批处理系统、作为其他算法的兜底。
- **算指标**：纯粹顺序推时间轴即可。

**（2）短作业优先 `SJF` / 短进程优先 `SPF`**

- **思想**：每次从就绪队列选**运行时间最短**的进程。
- **两个版本**：
  - **非抢占 `SJF`**：一旦开始跑就一直跑完，只在选择时比较。
  - **抢占式 `SRTN`（最短剩余时间优先）**：新进程到达时，若其运行时间**小于当前进程的剩余时间**，则抢占。
- **优点**：可以证明，**在所有作业同时到达（或不考虑到达时间）时，`SJF` 的平均等待时间与平均周转时间最小**。
- **缺点**：需要预知运行时间（实际靠估计）；**长作业可能饥饿**（一直被短作业插队）。
- **算指标**：每题都要先判断"该时刻有哪些进程已到达"，只在已到达者中挑最短的——这是最常见的失分点。

**（3）高响应比优先 `HRRN`**

- **思想**：综合"等待时间"与"运行时间"，每次选响应比最高者：
  `响应比 = (等待时间 + 要求服务时间) / 要求服务时间 = 1 + 等待时间 / 要求服务时间`。
- **抢占性**：**非抢占**（只在当前进程完成后才重新计算）。
- **为什么这么设计**：等待时间越长、运行时间越短，响应比越高。于是它**兼顾了 `FCFS`（等得久的有优势）与 `SJF`（短作业有优势）**，且**不会饥饿**（等得足够久，响应比一定涨上去）。
- **缺点**：每次调度都要计算所有候选进程的响应比，开销较大；仍需知道运行时间。

**（4）时间片轮转 `RR`**

- **思想**：就绪队列按 `FCFS` 排队，每个进程每次最多运行一个**时间片 `q`**；时间片用完就强制剥夺、排到队尾。
- **抢占性**：**抢占式**（由时钟中断驱动）。
- **关键**：
  - `q` **太大** ⇒ 退化成 `FCFS`；
  - `q` **太小** ⇒ 进程切换过于频繁，`CPU` 时间大量消耗在上下文切换上，实际效率下降；
  - `q` 应略大于一次典型的交互所需时间。
- **优点**：**响应快、公平**，所有进程都能在 `n*q` 时间内得到一次响应（`n` 为进程数），非常适合**分时系统**。
- **缺点**：不适合紧急任务（无优先级概念）；平均周转时间通常比 `SJF` 差；**新到达进程的插队位置会影响结果**，做题时必须按题目/教材约定的时机入队（默认：处理器切换时才把新到进程入队）。

**（5）优先级调度**

- **思想**：给每个进程一个优先级，每次选优先级最高者。
- **抢占性**：两者都有——抢占式优先级调度下，更高优先级到达即抢占。
- **优先级的确定**：静态优先级（创建时定死，简单但可能不公）vs 动态优先级（随等待时间增加而提高，可防饥饿）。
- **一般约定**：**系统进程 > 用户进程**；**交互型 > 非交互型**；**`I/O` 繁忙型 > `CPU` 繁忙型**（让 `I/O` 设备尽早忙起来，提高并行度）。
- **缺点**：**低优先级进程可能饥饿**（可用"动态优先级 + 老化"缓解）。

**（6）多级队列调度**

- **思想**：把就绪队列**按进程性质分成多个固定队列**（如系统进程队列、交互队列、批处理队列），队列之间**优先级固定**，队列内部各自用自己的算法（如交互队列用 `RR`，批处理队列用 `FCFS`）。
- **特点**：进程**固定在某个队列里，不能跨队列移动**；只有高优先级队列空了才调度低优先级队列。

**（7）多级反馈队列 `MLFQ`（`MLFQ`）**

- **思想**：设置 `n` 级就绪队列，**优先级从高到低、时间片从小到大**（常按 2 倍递增）。新进程进入**第 1 级**队列末尾：
  1. 按 `FCFS` 在各级内排队，先调度第 1 级；第 1 级空才调第 2 级……**只有高优先级队列空，才调低优先级**；
  2. 若进程在时间片内**用完**时间片仍未完成，就**降到下一级队列末尾**（时间片翻倍）；
  3. 若进程在时间片内**因等待 `I/O` 而主动放弃 `CPU`**，则**留在原队列**（甚至升级）；
  4. 若低优先级队列中的进程被新到达的高优先级进程**抢占**，则回到**原队列末尾**。
- **为什么优秀**：短作业（交互型）能在高优先级小时间片里迅速跑完；长作业（`CPU` 型）逐级降下去，用大时间片跑，减少切换；`I/O` 型进程始终留在高优先级，能及时响应——**综合了 `RR`、优先级、`SJF` 的长处**，是通用操作系统最常用的算法。
- **缺点**：实现复杂；**长作业若一直有短作业到达，可能饥饿**（各级队列都被占）。

**七个算法一览**

| 算法 | 抢占性 | 选择依据 | 主要优点 | 主要缺点 | 适用 |
| --- | --- | --- | --- | --- | --- |
| `FCFS` | 非抢占 | 到达顺序 | 简单、公平、不饥饿 | 对短作业与 `I/O` 型不利 | 批处理 |
| `SJF`/`SPF` | 非抢占 | 运行时间最短 | 平均周转/等待时间最优 | 需预知时间；长作业饥饿 | 批处理 |
| `SRTN` | 抢占 | 剩余时间最短 | 同上，且响应更及时 | 切换频繁、饥饿 | 批处理 |
| `HRRN` | 非抢占 | 响应比最高 | 兼顾长短、不饥饿 | 每次计算开销大 | 批处理 |
| `RR` | 抢占 | 队列顺序 + 时间片 | 响应快、公平 | 无优先级；`q` 难定 | 分时 |
| 优先级 | 两者皆有 | 优先级 | 可保证紧急任务 | 低优先级饥饿 | 实时、通用 |
| 多级队列 | 队列间抢占 | 队列优先级固定 | 分类管理 | 不灵活，不能跨队列 | 通用 |
| `MLFQ` | 抢占 | 级内 `FCFS` + 时间片 | 短作业、`I/O` 型、长作业都兼顾 | 复杂；长作业可能饥饿 | 通用/分时 |

> **408 怎么考 / 常见坑**
>
> - `SJF` "平均周转时间最短"的结论有**前提**：通常指所有作业**同时到达**或已全部到达的情形。有到达时间时，非抢占 `SJF` 不一定是最优，`SRTN` 也未必全局最优。
> - `HRRN` 的响应比公式写错是最常见的失分：**分子是"等待 + 要求服务"，不是"周转 + 服务"**。
> - `RR` 做题必须写清"新到达进程何时入队"。默认规则：**在本进程时间片用完、发生调度时才把新到达的进程插入就绪队列尾部**，且时间片用完的进程排在**新到者之后**。
> - `RR` 中若某进程在一个时间片内完成，不会再次入队；但**时间片未用完而阻塞**时不占满时间片。
> - `MLFQ` 的核心是"**用完时间片就降级、因 `I/O` 提前放弃就不降级**"，这条记反了整题就废了。
> - 抢占式调度常考"新进程到达时是否抢占"：`SRTN` 比较**剩余时间**，优先级调度比较**优先级**，`RR` 靠**时钟中断**。

#### 2.2.4 多处理机调度

- **处理器亲和性**：进程倾向于**一直在同一个 `CPU` 上运行**。因为频繁迁移会使 `Cache`、`TLB` 的命中率骤降，迁移代价可能超过负载均衡的收益。
  - **软亲和性**：尽量保持在同一 `CPU`，但允许迁移。
  - **硬亲和性**：用系统调用强制绑定某 `CPU`（`Linux` 的 `sched_setaffinity`）。
- **负载均衡**：让各 `CPU` 的负载大致相等，避免"一核有难、八核围观"。
  - **推迁移**：一个 `CPU` 发现自己的负载过高，主动把任务推给空闲 `CPU`。
  - **拉迁移**：空闲 `CPU` 主动从繁忙 `CPU` 的就绪队列里"偷"任务。
- **两种多处理机调度方式**：
  - **非对称多处理 `AMP`**：只有一个主处理器负责调度和 `I/O`，其余处理器只执行用户代码——实现简单，主处理器易成瓶颈。
  - **对称多处理 `SMP`**：所有处理器地位平等、共享同一就绪队列（或各有队列），都可调度——主流，但要处理并发访问就绪队列的互斥问题。
- 与单处理机的区别：单处理机任何时刻最多一个进程运行，多处理机上**真正并行**，调度要同时考虑"选谁"和"放到哪个 `CPU`"。

#### 2.2.5 上下文及其切换机制

- **上下文**：进程（或线程）运行时的**现场信息**，主要是 `CPU` 寄存器组（通用寄存器）、程序计数器 `PC`、程序状态字 `PSW`、栈指针，加上 `PCB` 中的状态与调度信息。
- **上下文切换的步骤**：
  1. 把当前进程的 `CPU` 现场**保存**到它的 `PCB`（或内核栈）中；
  2. 更新其 `PCB` 状态、把它挂到相应的队列；
  3. 从就绪队列选出新进程，**恢复**它的现场到 `CPU` 寄存器；
  4. 跳转到新进程上次中断处继续执行（可能还要切换页表、刷新 `TLB`，**这是大头开销**）。
- **切换开销来自**：保存/恢复寄存器、执行调度程序代码、切换地址空间（改页表基址寄存器、刷新 `TLB`/`Cache` 使命中率下降）。
- **进程切换 vs 线程切换**：
  - 同一进程内的**线程**切换**不换地址空间**，只需保存/恢复 `PC` 与寄存器（用户级线程甚至不用进内核），开销小。
  - **进程**切换要换地址空间，开销大。
  - 但**同进程内的内核级线程之间切换，仍需从用户态陷入内核**，开销和进程切换**相当**（王道反复考的坑）。
- **内核级线程与用户级线程的调度差别**：
  - **用户级线程**：内核只调度**进程**。线程的调度完全由**线程库**在用户态完成，内核不知道线程存在；一个线程阻塞系统调用会阻塞整个进程；无法利用多核。
  - **内核级线程**：内核直接调度**线程**，以线程为调度单位，一个线程阻塞不影响其他线程，可在多核上并行；切换需进内核。

> **408 怎么考 / 常见坑**
>
> - 常考"上下文切换不一定由中断引起"（也可能是进程主动阻塞、时间片到、系统调用）。
> - 常见坑：把"上下文切换的时间"算进进程的运行时间。**切换开销是纯开销**，不产生任何用户价值，时间片过小就会让它吃掉大量 `CPU`。
> - 亲和性的价值在于**保住 `Cache`/`TLB` 命中率**，不要答成"省内存"。

### 2.3 同步与互斥

#### 2.3.1 基本概念与四个原则

- **临界资源**：一次仅允许**一个进程**使用的资源（打印机、共享变量、共享缓冲区、文件）。
- **临界区**：进程中**访问临界资源**的那段代码（不是资源本身！）。
- 一个访问临界资源的进程的代码结构：

```c
/* 进入区（entry section）：检查并上锁，防止其他进程进入 */
/* 临界区（critical section）：真正访问临界资源的代码 */
/* 退出区（exit section）：解锁，允许其他进程进入 */
/* 剩余区（remainder section）：其余代码 */
```

- **同步（直接制约关系）**：为完成某个任务而建立的**协作**关系，进程间有明确的先后顺序。例：`A` 写完缓冲区，`B` 才能读。这是"**有序**"问题。
- **互斥（间接制约关系）**：多个进程争用同一临界资源，**排他**地使用。这是"**独占**"问题，谁先谁后不确定。
- 一句话区分：**同步讲先后，互斥讲独占**；同步是"我必须等你做完"，互斥是"我不能和你一起做"。

**访问临界区的四个原则**

| 原则 | 含义 | 为了什么 |
| --- | --- | --- |
| **空闲让进** | 临界区空闲时，应允许一个请求进入的进程立即进入 | 提高效率，不许空占着不用 |
| **忙则等待** | 已有进程在临界区时，其他试图进入的进程必须等待 | 保证**互斥** |
| **有限等待** | 对请求访问的进程，应保证它在**有限时间内**能进入 | 防止**饥饿/死等** |
| **让权等待** | 进程不能进入时应**释放 `CPU`**（进入阻塞），不能忙等 | 避免**忙等待**浪费 `CPU` |

**注意**：软件方法中的前三种（单标志、双标志先检查、双标志后检查）**都不满足"让权等待"**；`Peterson` 算法满足**空闲让进、忙则等待、有限等待**，但**仍不满足让权等待**（仍是忙等）。**硬件方法（`TestAndSet`、`Swap`）也不满足让权等待**。只有**信号量机制（记录型）**才真正满足让权等待。

#### 2.3.2 软件实现方法

设两个进程 `P0`、`P1`（用 `i`、`j` 表示，`j = 1 - i`）。

**（1）单标志法**

```c
int turn = 0;          /* turn 表示"现在轮到谁进" */

/* 进程 Pi */
while (turn != i) ;    /* 进入区：不是我就不停地等 */
/* 临界区 */
turn = j;              /* 退出区：让给对方 */
/* 剩余区 */
```

- 思想：用一个 `turn` 变量表示"轮到谁"。
- **缺陷**：**强制两个进程轮流进入**。若 `P0` 不想进（在剩余区），`turn` 却是 `1` 而 `P1` 已经进过一次，`P1` 就再也进不去——**违背"空闲让进"**。
- 满足：忙则等待、有限等待（轮流制下必然轮到自己）；不满足：空闲让进、让权等待。

**（2）双标志先检查法**

```c
bool flag[2] = {false, false};   /* flag[i] 表示 Pi 想进 */

/* 进程 Pi */
while (flag[j]) ;      /* ① 先检查对方是否想进 */
flag[i] = true;        /* ② 再表明自己想进 */
/* 临界区 */
flag[i] = false;       /* 退出区 */
/* 剩余区 */
```

- 思想：各自设标志表示意愿，先看对方再表态。
- **缺陷**：**检查和上锁不是原子操作**（中间可能发生进程切换）。若 `P0` 执行完 ① 后切到 `P1`，`P1` 也通过 ①，然后两者都置 `true`，**同时进入临界区**——**违背"忙则等待"**。
- 满足：空闲让进（都空闲时都能进）；不满足：忙则等待、让权等待。

**（3）双标志后检查法**

```c
bool flag[2] = {false, false};

/* 进程 Pi */
flag[i] = true;        /* ① 先表明自己想进 */
while (flag[j]) ;      /* ② 再检查对方 */
/* 临界区 */
flag[i] = false;
/* 剩余区 */
```

- 思想：先把"我想进"挂出去，再看对方。
- **缺陷**：若 `P0` 置 `flag[0] = true` 后切换，`P1` 也置 `flag[1] = true`，双方都在 `while` 里死等，**谁也进不去**——**违背"空闲让进"，且造成饥饿**。
- 满足：忙则等待；不满足：空闲让进、有限等待、让权等待。

**（4）`Peterson` 算法**

```c
bool flag[2] = {false, false};
int turn = 0;

/* 进程 Pi，j = 1 - i */
flag[i] = true;            /* ① 我想进 */
turn = j;                  /* ② 但"谦让"：先让对方进 */
while (flag[j] && turn == j) ;   /* ③ 对方想进且轮到对方，我就等 */
/* 临界区 */
flag[i] = false;           /* 退出区 */
/* 剩余区 */
```

- 思想：**"标志 + 谦让"**。两个人都想进时，谁最后写了 `turn`，谁就"更礼貌"，让对方先进；写成 `turn = j` 的进程在判断时一定不满足 `turn == j`，从而被迫等待。
- **优点**：**同时满足空闲让进、忙则等待、有限等待**，是软件方法中最完善的。
- **缺陷**：仍是**忙等待**，**不满足让权等待**；且现代 `CPU` 的乱序执行可能打破其正确性（实际要靠内存屏障）。
- 说理记忆法：两人都想进时，`turn` 只能是 `0` 或 `1` 之一，所以**必有一人**发现条件不成立而进入；不会两人都进（互斥），也不会两人都等（空闲让进）。

**四种软件方法对比**

| 方法 | 空闲让进 | 忙则等待 | 有限等待 | 让权等待 | 核心缺陷 |
| --- | --- | --- | --- | --- | --- |
| 单标志法 | 否 | 是 | 是 | 否 | 强制轮流，一方不进则另一方也进不去 |
| 双标志先检查 | 是 | **否** | 否 | 否 | 检查与上锁不原子，可能同时进入 |
| 双标志后检查 | **否** | 是 | **否** | 否 | 互相谦让，可能都进不去（饥饿） |
| `Peterson` | 是 | 是 | 是 | 否 | 仍是忙等待 |

> **坑的记法**：先检查的毛病是"**都进得去**"（违背忙则等待），后检查的毛病是"**都进不去**"（违背空闲让进）。

#### 2.3.3 硬件实现方法

**（1）中断屏蔽方法**

- 做法：进入临界区前**关中断**，出来后**开中断**。关中断后时钟中断与 `I/O` 中断都不会发生，进程切换不可能，自然互斥。
- 优点：简单、高效。
- 缺点：**只适用于单处理机**（多处理机上关掉一个 `CPU` 的中断，别的 `CPU` 照样跑）；关中断会**影响系统响应并发事件的能力**（时钟、`I/O` 都停了）；关中断权限只给**内核态**代码，不适合用户程序；临界区过长会严重降低系统效率。

**（2）`TestAndSet`（`TSL`）指令：硬件原子地"测试并设置"**

```c
/* 硬件保证此函数"原子"执行，即执行期间不会被中断 */
bool TestAndSet(bool *lock) {
    bool old = *lock;    /* 取出旧值 */
    *lock = true;        /* 立即置为已上锁 */
    return old;          /* 返回旧值 */
}

/* 使用 */
while (TestAndSet(&lock)) ;   /* 返回 true 表示刚才已上锁，继续等 */
/* 临界区 */
lock = false;                 /* 退出区：解锁 */
/* 剩余区 */
```

- 思想：把"读旧值 + 写新值"合成一条**不可分割的硬件指令**，从而消除双标志先检查中"检查与上锁之间有窗口"的问题。
- 满足：空闲让进、忙则等待、有限等待；**不满足让权等待**（忙等）。

**（3）`Swap` 指令：硬件原子地交换两个字的内容**

```c
/* 硬件保证原子的交换 */
void Swap(bool *a, bool *b) {
    bool tmp = *a;
    *a = *b;
    *b = tmp;
}

/* 使用 */
bool key = true;
do {
    Swap(&lock, &key);        /* 原子交换：把 lock 的值换给我 */
} while (key);                /* 换过来的是 true ⇒ 已被别人上锁，继续等 */
/* 临界区 */
lock = false;                 /* 退出区 */
/* 剩余区 */
```

- 与 `TestAndSet` 思想相同（都是把关键动作做成原子指令），区别只是**用交换而非测试并设置**实现。
- 同样**不满足让权等待**。

**三种硬件方法对比**

| 方法 | 适用环境 | 是否忙等 | 主要问题 |
| --- | --- | --- | --- |
| 中断屏蔽 | 仅单处理机、内核态代码 | 否 | 影响系统并发响应；用户程序无权使用 |
| `TestAndSet` | 单/多处理机均可 | 是 | 浪费 `CPU`；可能不满足有限等待（看实现） |
| `Swap` | 单/多处理机均可 | 是 | 同上 |

#### 2.3.4 锁

**自旋锁 vs 互斥锁**

| 对比项 | 自旋锁 `spinlock` | 互斥锁 `mutex` |
| --- | --- | --- |
| 等待方式 | **忙等待**（循环测试锁，`CPU` 空转） | **阻塞等待**（进阻塞队列，让出 `CPU`） |
| 是否让权 | 否（不满足让权等待） | 是（满足让权等待） |
| 切换开销 | 无进程切换，省下上下文切换时间 | 有两次进程切换（阻塞 + 唤醒） |
| 适用场景 | **临界区极短**、多处理机上（等待期间别的核还在干活） | 临界区较长、单处理机 |
| 缺点 | 临界区长时严重浪费 `CPU`；单处理机上纯属浪费时间 | 切换开销大 |
| 实现层面 | 多用 `TestAndSet`/`Swap` 指令实现 | 基于信号量/条件变量，需内核支持 |

**怎么选**：临界区执行时间 **小于** 两次上下文切换时间时，自旋更划算；否则阻塞更划算。单处理机上自旋锁基本没有价值（等待者自旋时持有者根本得不到 `CPU`）。

**锁的粒度**：锁保护的范围越小、并发度越高，但加锁解锁的频率也越高——"粗锁简单但并发低，细锁并发高但易死锁/易错"。

#### 2.3.5 信号量

**为什么需要信号量**：软件方法与硬件方法要么不正确，要么忙等。`Dijkstra` 提出信号量机制：**用一对原语 `P`、`V` 对信号量进行操作，把"判断 + 排队 + 唤醒"交给操作系统**，从而实现"让权等待"。

**（1）整型信号量**

```c
int S = 1;                 /* 只表示"资源数量" */

void wait(int *S) {        /* P 操作 */
    while (*S <= 0) ;      /* 资源不够就死等——忙等，不满足让权等待 */
    (*S)--;
}

void signal(int *S) {      /* V 操作 */
    (*S)++;
}
```

- 缺点：`while (*S <= 0)` 是忙等，**不满足"让权等待"**。

**（2）记录型信号量**（408 默认用这种）

```c
typedef struct {
    int value;                /* 剩余资源数 */
    struct process *L;        /* 等待队列（阻塞队列） */
} semaphore;

/* P 操作（wait）：申请一个资源 */
void wait(semaphore *S) {
    S->value--;
    if (S->value < 0) {
        /* 资源已分配完，把自己加入 S->L，并阻塞（主动让出 CPU） */
        block(S->L);
    }
}

/* V 操作（signal）：释放一个资源 */
void signal(semaphore *S) {
    S->value++;
    if (S->value <= 0) {
        /* 仍有进程在等待，唤醒其中一个（从阻塞变就绪） */
        wakeup(S->L);
    }
}
```

**`P`、`V` 的物理意义（记住这张表，几乎所有 `P`/`V` 题都能推出来）**

| 情形 | `S.value` 的取值 | 含义 |
| --- | --- | --- |
| `P` 之后 `S.value < 0` | `-k` | 有 `k` 个进程正在该信号量的等待队列里**阻塞** |
| `P` 之后 `S.value >= 0` | `k` | 还有 `k` 个该类资源可用 |
| `V` 之后 `S.value <= 0` | `-k` | 说明刚才有人等着，唤醒了一个，队列里还剩 `k` 个 |
| `V` 之后 `S.value > 0` | `k` | 没有人在等，资源数变为 `k` |

- **`P` 操作 = 申请资源**：先减再判断，减成负数就阻塞自己。
- **`V` 操作 = 释放资源**：先加再判断，加完仍 `<= 0` 说明有人在等，唤醒一个。
- **`P`、`V` 都必须是原子操作**（用关中断或硬件指令保证），否则 `value` 会出错。

**（3）三种用法**

**用法一：用信号量实现互斥**

```c
semaphore mutex = 1;      /* 初值 = 1，表示"一把锁" */

/* 进程 Pi */
P(mutex);                 /* 进入区：加锁 */
/* 临界区 */
V(mutex);                 /* 退出区：解锁 */
```

- **初值一定为 `1`**（临界资源只有一个）。
- **`P`、`V` 必须成对出现在同一个进程内**，且 `P` 要在临界区前、`V` 要在临界区后。
- 做题时**互斥信号量的名字可以不同（`mutex`、`lock`），但初值必须是 `1`**。

**用法二：用信号量实现同步**

```c
semaphore S = 0;          /* 初值 = 0，表示"事件还没发生" */

/* 进程 A：先执行代码 A1，然后给 B 发信号 */
A1;
V(S);

/* 进程 B：等 A 完成 A1 后再执行 B1 */
P(S);
B1;
```

- **"前操作之后执行 `V`，后操作之前执行 `P`"**，初值为 `0`。
- `P`、`V` 出现在**不同进程**中（与互斥的"同一进程内成对"正好相反）。

**用法三：实现前驱关系**

前驱图：`S1 → S2`，`S1 → S3`，`S2 → S4`……做法是**每条有向边设一个信号量，初值为 `0`；边的起点之后 `V`，边的终点之前 `P`**：

```c
semaphore a = 0, b = 0, c = 0, d = 0;   /* 每条边一个信号量 */

/* 进程 1 */  S1; V(a); V(b);
/* 进程 2 */  P(a); S2; V(c);
/* 进程 3 */  P(b); S3; V(d);
/* 进程 4 */  P(c); P(d); S4;
```

- 结点有几条入边就几个 `P`，有几条出边就几个 `V`。

> **408 怎么考 / 常见坑**
>
> - **初值判断**：互斥 ⇒ `1`；同步（"等一个事件"）⇒ `0`；"允许 `n` 个进程同时进入" ⇒ `n`。
> - **顺序写反的后果（必考）**：以生产者-消费者为例，若把两个 `P` 的顺序写成 `P(mutex); P(empty);`，当缓冲区**已满**时，生产者先占住 `mutex` 再在 `empty` 上阻塞；消费者要进入临界区却发现 `mutex` 被占，也阻塞——**双方互等，死锁**。记忆口诀：**"先 `P` 资源信号量，再 `P` 互斥信号量；`V` 的顺序无所谓"**。
> - **`P`、`V` 不能写反**：`P` 是申请（减），`V` 是释放（加）。
> - 信号量的值 `-k` 表示**等待队列中的进程数**，这是选择题的高频点。
> - 一般**互斥信号量只有一个**（即使有多个生产者、多个消费者，缓冲区还是一个临界资源）。
> - 忘记 `V` ⇒ 别人永远等（**死锁/饥饿**）；忘记 `P` ⇒ **互斥失效**。

#### 2.3.6 条件变量（大纲未单列，了解即可）

**为什么需要它**：`P` 操作阻塞后，只有当别人 `V` 时才会被唤醒。但有些场合希望"**条件不满足就等，条件变了再由别的线程通知**"，而且不希望像信号量那样"有多余的 `V` 就被消费掉"。这就是**条件变量**。

- 通常配合**互斥锁**使用：

```c
/* 典型用法（伪代码） */
lock(mutex);
while (!condition)          /* 必须用 while 而不是 if：防止虚假唤醒 */
    wait(cond, mutex);      /* 原子地"释放 mutex 并阻塞"，被唤醒时重新获得 mutex */
/* 条件成立，访问共享数据 */
unlock(mutex);

/* 另一边：改变条件后通知 */
lock(mutex);
condition = true;
signal(cond);               /* 唤醒一个等待者；broadcast 唤醒全部 */
unlock(mutex);
```

**与信号量的区别**

| 对比项 | 信号量 | 条件变量 |
| --- | --- | --- |
| 是否有计数值 | 有（`value` 记录资源数，`V` 可"攒着"） | **无**，不记录历史；没有等待者时 `signal` 是空操作 |
| 能否单独使用 | 能（`P`/`V` 自足） | **必须配合互斥锁**使用 |
| 唤醒语义 | `V` 使 `value++`，效果会保留 | `signal` 只在当前有等待者时有效 |
| 典型用途 | 计数型资源、同步前驱 | 等待某个条件成立（如"缓冲区非空"） |
| 虚假唤醒 | 不涉及 | 要用 `while` 循环重新检查条件 |

> **408 怎么考 / 常见坑**：大纲未单列，选择题偶有涉及"条件变量必须与互斥锁配合使用""条件变量没有计数功能""必须用 `while` 而非 `if` 检查条件"。

#### 2.3.7 经典同步问题（`P`/`V` 代码可背诵版）

**（1）生产者-消费者问题**

**描述**：一组生产者进程与一组消费者进程共享一个**大小为 `n` 的缓冲区**。生产者不能在缓冲区满时放数据，消费者不能在缓冲区空时取数据，且对缓冲区的访问必须互斥。

**信号量设置**：

- `mutex`：互斥访问缓冲区，初值 **`1`**
- `empty`：空闲缓冲区数量，初值 **`n`**
- `full`：已装数据的缓冲区数量，初值 **`0`**

```c
semaphore mutex = 1;   /* 互斥访问缓冲区 */
semaphore empty = n;   /* 空闲缓冲块数，初值 = 缓冲区大小 n */
semaphore full  = 0;   /* 产品数量，初值 = 0 */

/* 生产者 */
void producer() {
    while (1) {
        produce_item();          /* 生产一个数据 */
        P(empty);                /* ① 申请一个空缓冲块（资源信号量先 P） */
        P(mutex);                /* ② 再申请临界区（互斥信号量后 P） */
        put_item_into_buffer();  /* 临界区：放入缓冲区 */
        V(mutex);                /* ③ 退出临界区 */
        V(full);                 /* ④ 产品数 +1，通知消费者 */
    }
}

/* 消费者 */
void consumer() {
    while (1) {
        P(full);                 /* ① 先看有没有产品 */
        P(mutex);                /* ② 再进临界区 */
        take_item_from_buffer();  /* 临界区：取出产品 */
        V(mutex);                /* ③ 退出临界区 */
        V(empty);                /* ④ 空缓冲块 +1，通知生产者 */
        consume_item();          /* 消费数据 */
    }
}
```

**要点与坑**：

- **两个 `P` 的顺序不能颠倒**（先 `P(empty)`/`P(full)`，再 `P(mutex)`），否则缓冲区满/空时会**死锁**（见 2.3.5 的说明）。**两个 `V` 的顺序无所谓**。
- `V(empty)` / `V(full)` 一般放在**临界区外**（放在临界区内也不会错，但会加长临界区）。
- `mutex` 只有**一个**，即使有多个生产者也是如此。
- 若题目说"缓冲区大小为 `1`"，可以把 `mutex` 省掉（`empty`/`full` 已能保证互斥），但**建议照写不误**，多写不扣分。

**（2）多生产者-多消费者问题**

如有父亲、母亲、儿子、女儿四人共享一个盘子（容量 1）：父亲放苹果、母亲放橘子，儿子吃橘子、女儿吃苹果。要点：

- **盘子是临界资源**，`mutex` 仍只需一个。
- 但"苹果"和"橘子"是**两类不同资源**，必须用**两个不同的同步信号量**：`apple = 0`、`orange = 0`，而不能共用一个 `full`。
- 若把两种产品混用一个信号量，会出现"儿子被唤醒却发现盘里是苹果"的错误唤醒（需要重新判断，逻辑变复杂）。

```c
semaphore mutex = 1;         /* 盘子互斥 */
semaphore apple = 0;         /* 盘中苹果数（0 或 1） */
semaphore orange = 0;        /* 盘中橘子数（0 或 1） */
semaphore plate = 1;         /* 盘子是否为空，初值 1 */

/* 父亲 */  while(1){ P(plate); P(mutex); 放苹果; V(mutex); V(apple); }
/* 母亲 */  while(1){ P(plate); P(mutex); 放橘子; V(mutex); V(orange); }
/* 儿子 */  while(1){ P(orange); P(mutex); 取橘子; V(mutex); V(plate); 吃橘子; }
/* 女儿 */  while(1){ P(apple);  P(mutex); 取苹果; V(mutex); V(plate); 吃苹果; }
```

**（3）读者-写者问题**

**描述**：多个读者可同时读，写者必须独占。要求"读-读"允许、"读-写"互斥、"写-写"互斥。要区分两种偏袒策略。

**读者优先（读者不会被写者阻塞，写者可能饥饿）**

```c
semaphore rw = 1;        /* 读写互斥：第一个读者拿锁，最后一个读者放锁 */
semaphore mutex = 1;     /* 互斥访问 count */
int count = 0;           /* 当前正在读的读者数 */

/* 读者 */
void reader() {
    while (1) {
        P(mutex);
        if (count == 0) P(rw);   /* 第一个读者负责锁住写者 */
        count++;
        V(mutex);
        reading();               /* 多个读者可同时读 */
        P(mutex);
        count--;
        if (count == 0) V(rw);   /* 最后一个读者解锁，写者才有机会 */
        V(mutex);
    }
}

/* 写者 */
void writer() {
    while (1) {
        P(rw);                   /* 写者之间也互斥 */
        writing();
        V(rw);
    }
}
```

- **核心技巧**：用 `count` 记录读者数，**第一个读者加锁、最后一个读者解锁**，于是"读-读"可以并发，而"读-写"仍然互斥。
- **`count` 是共享变量**，所以它自己的 `++`/`--` 也要用 `mutex` 保护。
- **问题**：只要有读者源源不断到来，`count` 永远不为 `0`，写者一直等待——**写者饥饿**。

**写者优先（写者到来后，后续读者必须等）**

```c
semaphore rw = 1;         /* 读写互斥 */
semaphore mutex = 1;      /* 保护 count */
semaphore w = 1;          /* 写者优先的关键：写者到达时拦截新读者 */
int count = 0;

/* 读者 */
void reader() {
    while (1) {
        P(w);                /* 若有写者在等/在写，读者在此排队 */
        P(mutex);
        if (count == 0) P(rw);
        count++;
        V(mutex);
        V(w);                /* 进入计数后立刻放行，后面的读者还能进 */
        reading();
        P(mutex);
        count--;
        if (count == 0) V(rw);
        V(mutex);
    }
}

/* 写者 */
void writer() {
    while (1) {
        P(w);                /* 写者到达，先挡住新读者 */
        P(rw);
        writing();
        V(rw);
        V(w);
    }
}
```

- 加一个互斥信号量 `w`：写者一到就 `P(w)` 把"入口"占住，新读者被挡在 `w` 上；写者结束后 `V(w)` 放行。**效果是"写者优先"，代价是读者可能饥饿。**

**（4）哲学家进餐问题**

**描述**：5 位哲学家围圆桌，两两之间一只筷子（共 5 只）。哲学家交替思考与进餐，进餐需**同时拿到左右两只筷子**。

**有问题的原始写法**（每人先拿左再拿右）：若 5 人同时拿起左边的筷子，就会**互相等待右边的筷子**——典型的**循环等待死锁**。

```c
semaphore chopstick[5] = {1,1,1,1,1};   /* 每只筷子一个互斥信号量 */

/* 哲学家 i（错误示范：可能死锁） */
void philosopher(int i) {
    while (1) {
        P(chopstick[i]);                 /* 先拿左边 */
        P(chopstick[(i + 1) % 5]);       /* 再拿右边 */
        eating();
        V(chopstick[i]);
        V(chopstick[(i + 1) % 5]);
        thinking();
    }
}
```

**四种防死锁方案（任选其一，都要能写）**

1. **至多允许 4 人同时取筷子**（破坏"循环等待"）：加一个初值为 `4` 的信号量 `S`，取筷子前 `P(S)`、放筷子后 `V(S)`。5 人中至少 1 人拿不到筷子，环就断了。

```c
semaphore S = 4;                     /* 最多 4 人同时尝试 */
P(S); P(chopstick[i]); P(chopstick[(i+1)%5]);
eating();
V(chopstick[i]); V(chopstick[(i+1)%5]); V(S);
```

2. **奇数号先拿左、偶数号先拿右**（破坏"循环等待"）：编号小的筷子先拿，最后一人顺序相反。

```c
if (i % 2 == 0) {                    /* 偶数：先左后右 */
    P(chopstick[i]); P(chopstick[(i+1)%5]);
} else {                             /* 奇数：先右后左 */
    P(chopstick[(i+1)%5]); P(chopstick[i]);
}
```

3. **仅当左右两只筷子都可同时拿起时才允许拿**（破坏"请求并保持"）：用一个互斥信号量把所有取筷子的动作做成临界区。

```c
semaphore mutex = 1;
P(mutex);
P(chopstick[i]); P(chopstick[(i+1)%5]);
V(mutex);
```

4. **规定必须一次拿两只**（`AND` 型信号量，破坏"请求并保持"）：`Swait(chopstick[i], chopstick[(i+1)%5])` 一次申请两个资源，全成功才分配。

**对比表：经典同步问题一览**

| 问题 | 关键信号量 | 初值 | 核心难点 |
| --- | --- | --- | --- |
| 生产者-消费者 | `mutex` / `empty` / `full` | `1` / `n` / `0` | 两个 `P` 的顺序（资源先、互斥后） |
| 多生产者-多消费者 | `plate` / `apple` / `orange` | `1` / `0` / `0` | 不同产品要用不同信号量 |
| 读者-写者（读者优先） | `rw` / `mutex` / `count` | `1` / `1` / `0` | 首个读者加锁、末个读者解锁 ⇒ 写者饥饿 |
| 读者-写者（写者优先） | 再加 `w` | `1` | 写者到先 `P(w)` 拦住新读者 ⇒ 读者饥饿 |
| 哲学家进餐 | `chopstick[5]`（+`S` 或 `mutex`） | `1` | 死锁；四种防死锁方案要会写 |

### 2.4 死锁

#### 2.4.1 基本概念与四个必要条件

**死锁的定义**：多个进程因**竞争资源**而造成的**互相等待**、若无外力介入则**永远无法推进**的僵局。

**四个必要条件（同时成立才可能死锁）**

| 条件 | 含义 | 一句话理解 |
| --- | --- | --- |
| **互斥条件** | 资源在某一时刻只能被一个进程占用 | 资源是独占的 |
| **不可剥夺条件**（不剥夺） | 进程已获得的资源在未使用完之前不能被强行夺走 | 拿到就不撒手 |
| **请求并保持条件**（请求和保持） | 进程已保持至少一个资源，又提出新请求，而新资源被占 | 拿着碗里的，看着锅里的 |
| **循环等待条件** | 存在进程—资源的**循环等待链**：`P0` 等 `P1` 的资源，`P1` 等 `P2` 的……`Pn` 等 `P0` 的 | 首尾相接，谁都不让 |

**死锁、饥饿、死循环的区别**

| 对比项 | 死锁 | 饥饿 | 死循环 |
| --- | --- | --- | --- |
| 现象 | 多个进程**互相等待**，全部无法推进 | 某进程**长期得不到**所需资源 | 进程在代码里**反复执行同一段逻辑**，出不来 |
| 涉及进程数 | **至少 2 个**（单进程不会死锁） | 可能只有 1 个 | 1 个 |
| 是否有环 | 通常存在循环等待 | **无环** | 无 |
| 是否占用 `CPU` | **不占用**（进程都阻塞了） | 可能占也可能不占（被调度时能跑） | **占用**（一直在跑） |
| 解除方式 | 需要外力（剥夺、撤销、回退） | 调度策略改变（老化）即可能缓解 | 修正程序逻辑 |
| 关系 | 死锁**必然**导致相关进程饥饿 | 饥饿**不一定**是死锁 | 与死锁无关 |
| 是否一定死 | 是（无外力） | 不一定（可能最终得到） | 是（程序逻辑错误） |

**死锁处理的四个层次**

1. **鸵鸟策略**：不理会（忽略死锁，靠重启）。多数通用系统实际如此。
2. **死锁预防**：**事先**破坏四个必要条件之一，使死锁**不可能发生**。代价是资源利用率低。
3. **死锁避免**：**运行时**判断分配是否会导致系统进入**不安全状态**，只做"安全"的分配（银行家算法）。代价是每次分配都要做安全性检查。
4. **死锁检测与解除**：**允许**死锁发生，**事后**用资源分配图检测，再剥夺/撤销/回退来解除。

#### 2.4.2 死锁预防

**逐个破坏四个必要条件**

| 破坏哪个条件 | 具体做法 | 代价 / 问题 |
| --- | --- | --- |
| 破坏互斥条件 | **一般做不到**（很多资源本身就是独占的，如打印机） | 只能对少数可共享资源（如只读文件）做，通用性差；所以通常不从这里下手 |
| 破坏不可剥夺条件 | ① 进程申请新资源失败时，**立即释放**已占有的全部资源，日后再重新申请；② 允许**剥夺**：由系统把资源从占用者手中强行夺走 | 实现复杂、代价大；前一方案会**反复申请释放**，可能饥饿；剥夺会造成前段工作失效 |
| 破坏请求并保持条件 | **静态分配（一次性分配）**：进程在运行前**一次性申请所需的全部资源**，不齐就不运行，运行中不再申请 | 资源浪费严重、利用率低；可能**饥饿**（长期凑不齐）；进程可能"提前占着暂时用不到的"资源 |
| 破坏循环等待条件 | **顺序资源分配法**：给资源编号，进程**只能按编号递增的顺序**申请资源 | 限制编程自由；编号必须相对稳定；实际申请顺序常与编号矛盾，需要重排；**这是预防中最常用、代价相对小的一种** |

**要点**：破坏"互斥"通常不可行，所以常说的是"破坏后三个条件"。破坏请求并保持与破坏不可剥夺都靠**降低资源利用率**换安全；破坏循环等待靠**约定顺序**，代价最小。

#### 2.4.3 死锁避免与银行家算法

**安全状态与安全序列**

- **安全序列**：在某一时刻，存在一个进程的排列 `P1, P2, ..., Pn`，使得按这个顺序依次为每个进程分配它**还需要的全部资源**（`Need`），都能顺利满足并运行完成。
- **安全状态**：系统在某一时刻**能找到至少一条安全序列**。
- **不安全状态**：**找不到任何安全序列**。

**关键结论（必背）**

- 安全状态 **⇒ 一定不会死锁**（按安全序列分配就能全部完成）。
- 不安全状态 **⇒ 不一定死锁，只是"有可能"死锁**（后面如果进程的实际请求顺序恰好友好，仍可能走完）。**"不安全"≠"死锁"**，这是选择题最爱设的陷阱。
- 死锁状态 **⇒ 一定是不安全状态**。
- 关系链：`死锁 ⊆ 不安全状态`，且 `安全状态 ∩ 死锁 = 空集`。

```text
   ┌─────────────── 所有可能状态 ───────────────┐
   │  安全状态（无死锁）  │  不安全状态          │
   │                      │  ┌──────────────┐   │
   │                      │  │   死锁状态   │   │
   │                      │  └──────────────┘   │
   └──────────────────────┴──────────────────────┘
```

**银行家算法的数据结构**（设 `n` 个进程、`m` 类资源）

- `Available[m]`：系统当前**可用**的各类资源数
- `Max[n][m]`：每个进程对各类资源的**最大需求**
- `Allocation[n][m]`：每个进程**已分配**到的资源数
- `Need[n][m]`：每个进程**还需要的资源数**

**核心恒等式**：`Need = Max - Allocation`

**隐含关系**：`Available = 系统资源总量 - 所有进程的 Allocation 之和`

**安全性检查算法（手算五步）**

1. 令 `Work = Available`，`Finish[i] = false`（所有进程）。
2. 找一个满足 `Finish[i] == false` 且 `Need[i] <= Work`（**每一项都 <=**）的进程 `i`。
3. 若找到，则假定它完成并释放资源：`Work = Work + Allocation[i]`，`Finish[i] = true`，回到第 2 步。
4. 若找不到这样的进程，检查是否所有 `Finish[i]` 都为 `true`：**全为 `true` ⇒ 系统安全**，第 2 步中选出的顺序就是一条**安全序列**；**否则不安全**。
5. 手算时一定**每步写清 `Work` 的值**，这是采分点。

**请求能否满足的判断流程**（进程 `Pi` 发出请求向量 `Request_i`）

1. 检查 `Request_i <= Need_i`：若否，说明**请求超出最大需求**，报错（题目一般不会出现）。
2. 检查 `Request_i <= Available`：若否，说明**当前没有足够资源**，`Pi` 必须**等待**（不改数据结构）。
3. 前两步都通过，做**试探性分配**：
   - `Available = Available - Request_i`
   - `Allocation_i = Allocation_i + Request_i`
   - `Need_i = Need_i - Request_i`
4. 对**试探分配后的新状态**执行安全性检查：
   - **安全** ⇒ **正式分配**；
   - **不安全** ⇒ **撤销试探分配（回滚到原状态）**，`Pi` 等待。

> **408 怎么考 / 常见坑**
>
> - **`Need` 忘记更新**是最高频失分点：试探分配时 `Max` 不变，只有 `Available`、`Allocation`、`Need` 三个变。
> - **安全性检查里 `Work` 是动态变化的**：每找到一个可完成进程，`Work` 就要加上它的 `Allocation`（**不是加 `Need`，也不是加 `Max`**）。写"`Work = Work + Need`"直接零分。
> - "不安全 ⇒ 一定死锁"——**错**，只能说"**可能**死锁"。
> - "系统处于不安全状态时，只要进程不提出新请求就不会死锁"——这类表述要具体分析；标准结论只有"**安全状态一定无死锁**"。
> - 银行家算法属于**死锁避免**（不是预防），因为它不破坏四个必要条件，而是在运行时**动态判断**。选择题常拿"用银行家算法是死锁预防"来设错。
> - `Available` 的口径：题目给的可能是"资源总数"和 `Allocation` 矩阵，要自己先算 `Available = 总数 - 各列 Allocation 之和`。

#### 2.4.4 死锁检测与解除

**资源分配图**

- 顶点：**进程**（圆圈）与**资源**（方框，框内小圆点表示该类资源的**实例个数**）。
- **分配边**：资源 → 进程（一根边代表一个实例已分给该进程）。
- **请求边**：进程 → 资源（该进程在等这类资源的一个实例）。

**化简方法（死锁检测定理）**

1. 在图中找一个**既不阻塞又非孤立**的进程结点：它的**所有请求边都能被满足**（该类资源的空闲实例数够它请求的数量）。
2. 去掉它的所有请求边与分配边，使它成为**孤立结点**；释放的资源使别的进程可能变得不阻塞。
3. 重复 1、2，若最终**能消去图中所有边**，则该图**可完全简化**，**无死锁**；若**不能**，则**存在死锁**——此时**未被消去**的进程就是死锁进程。

**关于"环"的结论**

- 资源分配图中**存在环只是死锁的必要条件，不是充分条件**（`408` 常考）。
- **每类资源只有一个实例**时，**有环 ⇔ 死锁**。
- **某类资源有多个实例**时，**有环也可能不死锁**（环上的进程可以从别的实例获得资源而推进）。

**检测的时机**：死锁检测会带来开销，所以通常在**进程请求资源且分配不出去**时才做；也可按时间间隔周期性做。检测频率越高，越早发现，但开销越大。

**死锁解除的三种办法**

| 办法 | 做法 | 注意 |
| --- | --- | --- |
| **资源剥夺** | 从其他进程处**强行剥夺**足够资源分给死锁进程 | 被剥夺者可能要做"回退"，且可能被饿死 |
| **撤销进程** | 强行撤销部分甚至全部死锁进程，回收其资源 | 代价最大，要选"代价最小"的进程 |
| **进程回退** | 让进程**回退到**足以避开死锁的某个**检查点**，再重新推进 | 需要系统保存检查点，实现复杂 |

**"撤销哪个进程"的选取原则**（代价最小化）：优先级最低、已执行时间最短、已占用资源最少、剩余运行时间最长、是批处理进程而不是交互进程、所需资源种类最少。

> **408 怎么考 / 常见坑**
>
> - 常考"资源分配图中存在环是否一定死锁"：**每类资源单实例时一定；多实例时不一定**。
> - 常考"死锁检测中的化简"：化简顺序不唯一，能全部化简即无死锁。
> - "检测到死锁后必须撤销所有死锁进程"——错，可以只撤销**代价最小**的一部分。

### 2.5 大纲未单列但王道有的内容（了解即可）

- **管程（`Monitor`）（大纲未单列，了解即可）**：把"共享数据 + 对它的操作 + 同步机制"封装成一个模块，同一时刻**只能有一个进程在管程内活动**（互斥由编译器/语言机制自动保证），进程通过**条件变量**在管程内等待。它是"语言级"的同步工具，避免了程序员手写 `P`/`V` 时把顺序写错。`P`/`V` 代码题里**不要**用管程作答，但选择题可能问"管程的互斥由谁保证"（答：由**编译器/管程自身的机制**保证，不由程序员负责）。
- **线程库（大纲未单列，了解即可）**：`Pthreads` 是 `POSIX` 线程标准规定的接口，属于**用户级线程库**，但具体实现可以是内核级或组合方式。
- **`SMP` 与就绪队列的组织（大纲未单列，了解即可）**：对称多处理下，就绪队列可以是全局的（所有 `CPU` 抢一把锁）或每个 `CPU` 一个（配以推/拉迁移做负载均衡）。

### 表 6　安全状态与不安全状态

| 对比项 | 安全状态 | 不安全状态 |
| --- | --- | --- |
| 定义 | **存在**至少一条安全序列 | **找不到**任何安全序列 |
| 是否一定死锁 | **一定不会**死锁 | **可能**死锁，也**可能**不死锁 |
| 与死锁的关系 | 安全状态 ⊇ 无死锁；安全与死锁**互斥** | 死锁 ⊂ 不安全状态 |

| 经典陷阱 | "处于安全状态就一定不死锁"——**对** | "不安全就死锁"——**错**；"不安全时立刻回收资源"——**错**，应先让进程等待 |

### 表 7　其他高频易混

| 易混对象 | 区别要点 |
| --- | --- |
| 进程 vs 线程 | 进程是**资源分配**单位、有独立地址空间；线程是**调度**单位、共享进程地址空间 |
| 用户级线程 vs 内核级线程 | `ULT` 由线程库管、切换快、阻塞会拖累整个进程、不能用多核；`KLT` 由内核管、可并行、切换要进内核 |
| 阻塞 vs 挂起 | 阻塞是**等事件**（还在内存）；挂起是**被换出到外存**（可能就绪也可能阻塞） |
| 阻塞 vs 唤醒 | 阻塞是**主动**（自己 `block`）；唤醒是**被动**（别人 `wakeup`） |
| 临界资源 vs 临界区 | 临界资源是**资源本身**；临界区是**访问它的那段代码** |
| 自旋锁 vs 互斥锁 | 自旋是**忙等**（不满足让权等待），适合极短临界区/多处理机；互斥是**阻塞等待** |
| 信号量实现互斥 vs 实现同步 | 互斥：初值 `1`，同一进程内 `P`/`V` 成对；同步：初值 `0`，不同进程中配对 |
| 死锁 vs 饥饿 | 死锁至少 2 个进程、有环、都不占 `CPU`；饥饿可能只有 1 个进程、无环、可能占 `CPU` |
| 死锁 vs 死循环 | 死循环在**跑**（占 `CPU`），是程序逻辑错误；死锁在**等**（不占 `CPU`） |
| 死锁预防 vs 死锁检测 | 预防是**不让它发生**；检测是**允许发生，事后发现并解除** |
| 上下文切换 vs 进程切换 | 上下文切换是保存/恢复现场的动作（线程切换也是上下文切换）；进程切换还必须**换地址空间**，开销更大 |
| 中断屏蔽 vs 关中断实现原语 | 都是屏蔽中断，但目的不同：前者为**互斥**，后者为保证**原语原子性** |

## 四、例题精练（3 道 + 1 道加练）

> 以下题目均为**自编/真题风格改编**，不是真题原文。

### 例题 1（单项选择题）

**题目**　下列关于进程状态转换的叙述中，**不可能发生**的是（　　）。

A. 就绪态 → 运行态
B. 运行态 → 阻塞态
C. 阻塞态 → 运行态
D. 运行态 → 就绪态

**逐项解析**

- **A 可能**：就绪进程被**低级调度**（进程调度）选中，获得 `CPU` 后进入运行态。这是每次调度的常规动作。
- **B 可能**：正在运行的进程**主动**请求 `I/O`、申请资源失败或执行 `P` 操作不成功时，会**一步**从运行态直接进入阻塞态（不经过就绪态）。注意这是进程**自身**发起的行为。
- **C 不可能**：阻塞态进程是在**等待某事件**（如 `I/O` 完成、别人 `V` 操作）；一旦事件发生，它只能被**唤醒进入就绪态**，重新回到就绪队列排队，之后**再被调度**才可能进入运行态。**阻塞态的进程即使把 `CPU` 给它也跑不动**，所以"阻塞 → 运行"这一步不存在。（若要写也只能写成"阻塞 → 就绪 → 运行"两步。）
- **D 可能**：运行态进程的**时间片用完**，或被**更高优先级/更短剩余时间的进程抢占**时，会回到就绪态排队等待下次调度。

**答案**：**C**

**采分点与常见坑**

- 采分点：判断每个选项是否对应一个真实的**事件原因**——有原因才可能发生。
- 常见坑 1：误选 B，认为"运行态必须先到就绪态再阻塞"。**运行 → 阻塞是一步到位的**，这是被反复考的细节。
- 常见坑 2：误选 D，把"运行 → 就绪"当成不可能。时间片用完和抢占都会造成它，在抢占式系统中极常见。
- 常见坑 3：还有一对"不可能"要一起记住：**就绪 → 阻塞**（就绪进程没在 `CPU` 上，谈不到因等待事件而阻塞）。
- 一句话口诀：**阻塞只能被唤醒到就绪，就绪只能被调度到运行**。

### 例题 2（综合应用题：`CPU` 调度算法计算周转时间与带权周转时间）

**题目**　有 4 个进程 `P1`、`P2`、`P3`、`P4`，到达时间与要求服务时间如下表（单位：时间片）。忽略进程切换开销与 `I/O` 时间。

| 进程 | 到达时间 | 服务时间 |
| --- | --- | --- |
| `P1` | `0` | `7` |
| `P2` | `2` | `4` |
| `P3` | `4` | `1` |
| `P4` | `5` | `4` |

分别计算下列调度算法下各进程的完成时间、周转时间、带权周转时间，以及平均周转时间与平均带权周转时间：

1. `FCFS`
2. 非抢占式短作业优先（`SJF`）
3. 抢占式短作业优先（`SRTN`，按最短剩余时间抢占）
4. 时间片轮转 `RR`，时间片 `q = 1`

约定：`RR` 中"当前进程的时间片用完而发生调度时"，**先把在这 1 个时间片内新到达的进程按到达时间加入队尾，再把刚被剥夺的进程加入队尾**。

**通用公式（先写下来，再填表）**

- `周转时间 = 完成时间 - 到达时间`
- `带权周转时间 = 周转时间 / 服务时间`
- `平均周转时间 = 各进程周转时间之和 / 4`
- `平均带权周转时间 = 各进程带权周转时间之和 / 4`

**第 1 问：`FCFS`**

按到达顺序服务：`P1(0~7)`，接着 `P2(7~11)`、`P3(11~12)`、`P4(12~16)`。

调度顺序：`P1 → P2 → P3 → P4`

| 进程 | 到达 | 服务 | 开始 | 完成 | 周转时间 | 带权周转时间 |
| --- | --- | --- | --- | --- | --- | --- |
| `P1` | `0` | `7` | `0` | `7` | `7` | `7 / 7 = 1.00` |
| `P2` | `2` | `4` | `7` | `11` | `9` | `9 / 4 = 2.25` |
| `P3` | `4` | `1` | `11` | `12` | `8` | `8 / 1 = 8.00` |
| `P4` | `5` | `4` | `12` | `16` | `11` | `11 / 4 = 2.75` |

- `平均周转时间 = (7 + 9 + 8 + 11) / 4 = 35 / 4 = 8.75`
- `平均带权周转时间 = (1.00 + 2.25 + 8.00 + 2.75) / 4 = 14.00 / 4 = 3.50`

> 观察：`P3` 只需运行 `1` 个时间片，却等了 `7` 个，带权周转时间高达 `8`——这正是 `FCFS` "**对短作业不利**"的直观体现。

**第 2 问：非抢占式 `SJF`**

- `t = 0`：只有 `P1` 到达，`P1` 运行；非抢占，一次跑完，`0~7`。
- `t = 7`：已到达且未完成的有 `P2`（服务 `4`）、`P3`（服务 `1`）、`P4`（服务 `4`），选最短的 `P3`，`7~8`。
- `t = 8`：`P2` 与 `P4` 服务时间都是 `4`，按"先到达者优先"取 `P2`，`8~12`。
- `t = 12`：`P4`，`12~16`。

调度顺序：`P1 → P3 → P2 → P4`

| 进程 | 到达 | 服务 | 开始 | 完成 | 周转时间 | 带权周转时间 |
| --- | --- | --- | --- | --- | --- | --- |
| `P1` | `0` | `7` | `0` | `7` | `7` | `1.00` |
| `P2` | `2` | `4` | `8` | `12` | `10` | `10 / 4 = 2.50` |
| `P3` | `4` | `1` | `7` | `8` | `4` | `4 / 1 = 4.00` |
| `P4` | `5` | `4` | `12` | `16` | `11` | `11 / 4 = 2.75` |

- `平均周转时间 = (7 + 10 + 4 + 11) / 4 = 32 / 4 = 8.00`
- `平均带权周转时间 = (1.00 + 2.50 + 4.00 + 2.75) / 4 = 10.25 / 4 = 2.5625 ≈ 2.56`

> 注意：`P1` 一开始就抢占了 `CPU` 并跑到底，所以"短作业优先"只体现在 `t = 7` 之后。这说明**有到达时间时，非抢占 `SJF` 的优势被削弱**。
>
> **选择题常考的结论**：所有作业**同时到达**时，`SJF` 的平均等待时间、平均周转时间**最小**；有到达时间时这个结论**不再成立**（本题 `SJF` 与 `FCFS` 的 `P1` 完全一样，就是被到达时间限制住了）。

**第 3 问：抢占式 `SRTN`（最容易算错，逐时刻推进）**

规则：**每当有新进程到达或当前进程结束，就选"剩余时间最短"的进程运行**。

| 时刻 `t` | 发生了什么 | 已到达未完成者的剩余时间 | 决策 |
| --- | --- | --- | --- |
| `0` | `P1` 到达 | `P1: 7` | 运行 `P1` |
| `2` | `P2` 到达 | `P1: 5`（已跑 2），`P2: 4` | `4 < 5` ⇒ **`P2` 抢占** |
| `4` | `P3` 到达 | `P1: 5`，`P2: 2`（已跑 2），`P3: 1` | `1` 最短 ⇒ **`P3` 抢占** |
| `5` | `P3` 完成，`P4` 到达 | `P1: 5`，`P2: 2`，`P4: 4` | `P2` 最短 ⇒ 运行 `P2` |
| `7` | `P2` 完成 | `P1: 5`，`P4: 4`（已跑 0） | `P4` 最短 ⇒ 运行 `P4` |
| `11` | `P4` 完成 | `P1: 5` | 运行 `P1` |
| `16` | `P1` 完成 | — | 结束 |

运行片段：`P1(0~2) → P2(2~4) → P3(4~5) → P2(5~7) → P4(7~11) → P1(11~16)`

| 进程 | 到达 | 服务 | 首次开始 | 完成 | 周转时间 | 带权周转时间 |
| --- | --- | --- | --- | --- | --- | --- |
| `P1` | `0` | `7` | `0` | `16` | `16` | `16 / 7 ≈ 2.29` |
| `P2` | `2` | `4` | `2` | `7` | `5` | `5 / 4 = 1.25` |
| `P3` | `4` | `1` | `4` | `5` | `1` | `1 / 1 = 1.00` |
| `P4` | `5` | `4` | `7` | `11` | `6` | `6 / 4 = 1.50` |

- `平均周转时间 = (16 + 5 + 1 + 6) / 4 = 28 / 4 = 7.00`
- `平均带权周转时间 = (2.29 + 1.25 + 1.00 + 1.50) / 4 = 6.04 / 4 ≈ 1.51`

> 为什么 `SRTN` 的周转时间最好？因为它**每次把 `CPU` 给最"急着结束"的那个进程**，短作业迅速清空，长作业被不断推后但只影响它自己。代价是**`P1` 被反复打断**（`0~2`、`11~16`），它的带权周转时间反而比 `FCFS` 差——**平均指标好不等于每个进程都好**。
>
> **本题最容易算错的地方就是 `t = 2`**：`P1` 已运行 `2`，**剩余 `5`**；`P2` 的服务时间 `4` 就是它的剩余时间，因为 `4 < 5`，**`P2` 必须抢占**。如果错把"服务时间 `4` 与 `P1` 的服务时间 `7`"相比、或错算 `P1` 的剩余时间为 `3`，后面全盘皆错。

**第 4 问：`RR`，`q = 1`**

逐时间片推演（"新到者先入队、被剥夺者后入队"）：

| 时间段 | 运行 | 运行后剩余 | 就绪队列（左为队首） |
| --- | --- | --- | --- |
| `0~1` | `P1` | `6` | `P1` |
| `1~2` | `P1` | `5` | `t=2` 时 `P2` 到 ⇒ `P2`；再入 `P1` ⇒ `P2, P1` |
| `2~3` | `P2` | `3` | `P1, P2` |
| `3~4` | `P1` | `4` | `t=4` 时 `P3` 到 ⇒ `P2, P3`；再入 `P1` ⇒ `P2, P3, P1` |
| `4~5` | `P2` | `2` | `P3, P1, P2` |
| `5~6` | `P3` | `0`（**完成**） | `t=5` 时 `P4` 到 ⇒ `P1, P2, P4` |
| `6~7` | `P1` | `3` | `P2, P4, P1` |
| `7~8` | `P2` | `1` | `P4, P1, P2` |
| `8~9` | `P4` | `3` | `P1, P2, P4` |
| `9~10` | `P1` | `2` | `P2, P4, P1` |
| `10~11` | `P2` | `0`（**完成**） | `P4, P1` |
| `11~12` | `P4` | `2` | `P1, P4` |
| `12~13` | `P1` | `1` | `P4, P1` |
| `13~14` | `P4` | `1` | `P1, P4` |
| `14~15` | `P1` | `0`（**完成**） | `P4` |
| `15~16` | `P4` | `0`（**完成**） | 空 |

运行序列：`P1 P1 P2 P1 P2 P3 P1 P2 P4 P1 P2 P4 P1 P4 P1 P4`

各进程运行片段：

- `P1`：`0~2`、`3~4`、`6~7`、`9~10`、`12~13`、`14~15` ⇒ 完成时间 `15`
- `P2`：`2~3`、`4~5`、`7~8`、`10~11` ⇒ 完成时间 `11`
- `P3`：`5~6` ⇒ 完成时间 `6`
- `P4`：`8~9`、`11~12`、`13~14`、`15~16` ⇒ 完成时间 `16`

| 进程 | 到达 | 服务 | 完成 | 周转时间 | 带权周转时间 |
| --- | --- | --- | --- | --- | --- |
| `P1` | `0` | `7` | `15` | `15` | `15 / 7 ≈ 2.14` |
| `P2` | `2` | `4` | `11` | `9` | `9 / 4 = 2.25` |
| `P3` | `4` | `1` | `6` | `2` | `2 / 1 = 2.00` |
| `P4` | `5` | `4` | `16` | `11` | `11 / 4 = 2.75` |

- `平均周转时间 = (15 + 9 + 2 + 11) / 4 = 37 / 4 = 9.25`
- `平均带权周转时间 = (2.14 + 2.25 + 2.00 + 2.75) / 4 = 9.14 / 4 ≈ 2.29`

> **重要提醒 1**：`RR` 的结果**依赖于"新到达进程的入队时机"这一约定**。若题目采用"新进程一到就立即插队并抢占当前时间片"的约定，本题结果会变为 `P1` 完成 `12`、`P2` 完成 `8`、`P3` 完成 `9`、`P4` 完成 `16`，平均周转时间为 `8.50`。**答题时务必写出你所用的约定，并把就绪队列的每一步列清楚**，这样即使用数值略有差异，过程分也能拿到。
>
> **重要提醒 2**：本题 `RR` 的平均周转时间（`9.25`）**比 `FCFS`（`8.75`）还大**！这是反直觉但正确的事实：`RR` 平等对待所有进程，短作业 `P3` 也被反复插队，完成时间被拖长。`RR` 的价值在于**响应时间短、公平**（每个进程最多等 `n × q` 就能上一次 `CPU`），而**不在平均周转时间短**。这个结论是选择题常考点。

**五种算法结果汇总（按本题约定）**

| 算法 | 调度顺序 / 运行片段 | 平均周转时间 | 平均带权周转时间 |
| --- | --- | --- | --- |
| `FCFS` | `P1 P2 P3 P4` | `8.75` | `3.50` |
| 非抢占 `SJF` | `P1 P3 P2 P4` | `8.00` | `2.56` |
| 抢占 `SRTN` | `P1(0~2) P2(2~4) P3(4~5) P2(5~7) P4(7~11) P1(11~16)` | `7.00` | `1.51` |
| `RR (q=1)` | 见上表运行序列 | `9.25` | `2.29` |
| `RR (q=4)`（对照） | `P1(0~4) P2(4~8) P3(8~9) P1(9~12) P4(12~16)` | `8.50` | `2.74` |

> `q` 从 `1` 变成 `4`，平均周转时间从 `9.25` 降到 `8.50`——**时间片越大越接近 `FCFS`**，这就是"`q` 过大则 `RR` 退化为 `FCFS`"的数值印证。

**采分点与常见坑**

- **采分点 1**：必须**先写公式**（`周转时间 = 完成 - 到达`、`带权周转时间 = 周转 / 服务`），再列表计算；只给最终数字最多拿一半分。
- **采分点 2**：每个算法都要**写清调度顺序或时间轴**，这是过程分的核心。`SRTN` 要写出每个"抢占点"的比较过程。
- **采分点 3**：平均值要写出分子分母（如 `28 / 4 = 7.00`），不要只写 `7.00`。
- **常见坑 1**：算 `SJF`/`SRTN` 时把**尚未到达**的进程也拿来比较。`t = 7` 时只能从 `P2`、`P3`、`P4` 中选，不能把已经跑完的 `P1` 再拿来比。
- **常见坑 2**：`SRTN` 比较的是**剩余时间**，不是**服务时间**（`t = 2` 处最容易错，见上）。
- **常见坑 3**：带权周转时间算成小于 `1`（把等待时间当成了周转时间）。带权周转时间恒 `>= 1`，等于 `1` 说明一到达就运行且未被抢占。
- **常见坑 4**：忘记"非抢占"的含义——`SJF` 一旦开始就不被打断，只在进程结束时才重新选。
- **常见坑 5**：`RR` 不写清入队约定，导致数值与标答不符；应当**主动声明约定**。
- **常见坑 6**：把"平均周转时间最小"的错误结论套在 `RR` 上。最小的是 `SJF`/`SRTN`（且要求作业同时到达），`RR` 追求的是响应时间。
### 例题 3（综合应用题：用信号量 `P`/`V` 描述同步互斥）

**题目**　某系统有一个由 `n` 个缓冲区组成的环形缓冲区，`3` 个生产者进程和 `2` 个消费者进程并发工作：生产者把每次生产出的一个数据放入缓冲区，消费者从缓冲区取出一个数据处理。要求：

1. 定义所需的信号量并说明初值；
2. 用 `P`、`V` 操作写出生产者与消费者的同步互斥代码；
3. 说明若把生产者中两个 `P` 操作的顺序颠倒，会出现什么问题，并解释原因；
4. 若要求"只有当缓冲区中的产品数达到 `k`（`k <= n`）个时，消费者才批量取走 `k` 个"，应如何改动信号量的设置？

**第 1 问：信号量定义**

| 信号量 | 作用 | 初值 | 为什么是这个初值 |
| --- | --- | --- | --- |
| `mutex` | 互斥访问缓冲区（临界资源） | `1` | 缓冲区是**一个**临界资源，只需一把锁 |
| `empty` | 空闲缓冲区数量 | `n` | 初始时 `n` 个缓冲块全空 |
| `full` | 已装数据的缓冲区数量（产品数） | `0` | 初始时没有产品 |
| `batch`（第 4 问用） | 产品数是否达到 `k` | `0` | 达到 `k` 个时才通知消费者 |

> 注意：`mutex` **只需一个**，与生产者、消费者的个数无关；`empty + full = n` 恒成立。

**第 2 问：代码**

```c
#define N 100                       /* 缓冲区大小 n */

semaphore mutex = 1;                /* 互斥访问缓冲区 */
semaphore empty = N;                /* 空闲缓冲块数，初值 = n */
semaphore full  = 0;                /* 产品数，初值 = 0 */

int buffer[N];
int in = 0, out = 0;                /* 环形缓冲区的读写指针 */

/* ---------------- 生产者进程 ---------------- */
void producer() {
    while (1) {
        produce_item();             /* 生产一个数据 */
        P(empty);                   /* ① 资源信号量：申请一个空缓冲块 */
        P(mutex);                   /* ② 互斥信号量：进入临界区 */
        buffer[in] = item;          /* 临界区：放入数据 */
        in = (in + 1) % N;
        V(mutex);                   /* ③ 退出临界区 */
        V(full);                    /* ④ 产品数 +1，若有消费者在等则唤醒 */
    }
}

/* ---------------- 消费者进程 ---------------- */
void consumer() {
    while (1) {
        P(full);                    /* ① 资源信号量：申请一个产品 */
        P(mutex);                   /* ② 互斥信号量：进入临界区 */
        item = buffer[out];         /* 临界区：取出数据 */
        out = (out + 1) % N;
        V(mutex);                   /* ③ 退出临界区 */
        V(empty);                   /* ④ 空缓冲块 +1，若有生产者在等则唤醒 */
        consume_item(item);         /* 消费数据 */
    }
}
```

**第 3 问：两个 `P` 顺序颠倒的后果**

若写成 `P(mutex); P(empty);`，则**可能死锁**。原因：

- 设缓冲区**已满**（`empty = 0`，`full = n`）。
- 某生产者执行 `P(mutex)` 成功，**占住了缓冲区的锁**；接着执行 `P(empty)`，因 `empty = 0` 而**阻塞**。
- 此时消费者要取数据，必须执行 `P(mutex)`，但 `mutex` 已被那个生产者占着，消费者**也阻塞**。
- 消费者拿不到锁就无法取走数据、无法 `V(empty)`；生产者等不到 `empty` 变正就无法释放 `mutex`——**互相等待，死锁**。
- 记忆规则：**先 `P` 资源信号量（`empty`/`full`），再 `P` 互斥信号量（`mutex`）；两个 `V` 的顺序无所谓。**

**第 4 问：改成"批量取走 `k` 个"**

引入一个信号量 `batch`（初值 `0`）来同步"产品数够 `k` 个"这一事件，并用一个整型变量计数：

```c
semaphore mutex = 1;
semaphore empty = N;
semaphore full  = 0;
semaphore batch = 0;                /* 新增：产品数达到 k 的通知 */
int count = 0;                      /* 当前缓冲区中的产品数（受 mutex 保护） */

/* 生产者 */
void producer() {
    while (1) {
        produce_item();
        P(empty);                          /* ① 申请一个空缓冲块 */
        P(mutex);                          /* ② 进入临界区 */
        buffer[in] = item;
        in = (in + 1) % N;
        if (++count == K) V(batch);        /* ③ 恰好积满 k 个，通知消费者 */
        V(mutex);
        V(full);                           /* ④ 产品数 +1 */
    }
}

/* 消费者：一次取走 k 个 */
void consumer() {
    while (1) {
        P(batch);                          /* ① 等到产品数达到 k */
        for (int j = 0; j < K; j++) {      /* ② 逐个申请产品，共 k 个 */
            P(full);                       /*    资源信号量在前 */
            P(mutex);                      /*    互斥信号量在后 */
            item = buffer[out];
            out = (out + 1) % N;
            count--;
            V(mutex);
            V(empty);                      /*    每取走一个就归还一个空块 */
            consume_item(item);            /*    耗时操作放在临界区外 */
        }
    }
}
```

要点：

- **计数变量 `count` 是共享变量，必须放在 `mutex` 保护的临界区内**；它**只用于判断"是否恰好积满 `k`"**，产品数量本身仍由 `full`/`empty` 记录，两套机制不要混用。
- `batch` 的作用是"事件同步"（初值 `0`）；判断"恰好达到 `k`"用 `++count == K`，避免每放一个都 `V(batch)` 导致信号量被"攒"起来，消费者之后会连续取走不足 `k` 个的数据。
- 取 `k` 个就是**取 `k` 次**，每次都要成对写 `P(full)`/`V(empty)`，不能只写一次（标准信号量一次只加 `1`）。
- 若题目改成"缓冲区中产品数达到 `k` 就唤醒消费者"，另一种同样正确的写法是在生产者侧判断 `count >= K` 时 `V(batch)`，消费者取完后把 `count` 清零——关键是**判断与清零都在临界区内**。

**采分点与常见坑**

- **采分点 1**：三个基本信号量必须**写全且初值正确**（`mutex = 1`、`empty = n`、`full = 0`）；`mutex` 初值写成 `n` 或漏掉任意一个都不给分。第 4 问再额外说明 `batch = 0`。
- **采分点 2**：`P` 的顺序（资源在前、互斥在后）是**独立的得分点**，一定要按这个顺序写。
- **采分点 3**：生产者与消费者的代码要**各自成段**，不要把 `P`/`V` 混在同一个循环里。
- **采分点 4**：`P(mutex)` 与 `V(mutex)` **必须成对**，漏一个 `V` 会死锁。
- **常见坑 1**：把 `empty` 初值写成 `0`（与 `full` 弄反），导致一开始所有人都阻塞。
- **常见坑 2**：`V(empty)` 与 `V(full)` 写反——生产者应 `V(full)`（告诉消费者有产品了），消费者应 `V(empty)`（告诉生产者有空位了）。
- **常见坑 3**：在临界区内做 `consume_item()`（耗时的消费动作）。应把耗时操作放到**临界区外**，否则临界区过长、并发度低。本题代码已把 `consume_item` 放在 `V(mutex)` 之后。
- **常见坑 4**：第 4 问里忘记保护 `count`，或每放一个产品就 `V(batch)`（信号量被"攒"起来，之后消费者会连续取走不足 `k` 个的数据）。

### 例题 4（综合应用题：银行家算法安全性检查与请求判断）

> 大纲要求的三类综合应用题中，银行家算法是最"套路化"的一种，手算步骤固定，所以再补一道完整范例。**同样是自编题，不是真题。**

**题目**　系统有 `3` 类资源 `A`、`B`、`C`，资源总量为 `(9, 3, 9)`，现有 `5` 个进程 `P0 ~ P4`，`T0` 时刻的资源分配情况如下（单位：个）：

| 进程 | `Allocation`（`A B C`） | `Max`（`A B C`） |
| --- | --- | --- |
| `P0` | `0 1 0` | `7 5 3` |
| `P1` | `3 0 2` | `3 2 2` |
| `P2` | `3 0 2` | `9 0 2` |
| `P3` | `2 1 1` | `2 2 2` |
| `P4` | `0 0 2` | `4 3 3` |

回答：

1. 求 `Need` 矩阵与 `Available` 向量；
2. `T0` 时刻系统是否处于安全状态？若是，给出一条安全序列；
3. 若 `P1` 提出请求 `Request = (1, 0, 2)`，能否分配？
4. 若 `P1` 提出请求 `Request = (0, 2, 0)`，能否分配？

**第 1 问：`Need` 与 `Available`**

核心恒等式：`Need = Max - Allocation`

| 进程 | `Max` | `Allocation` | `Need = Max - Allocation` |
| --- | --- | --- | --- |
| `P0` | `7 5 3` | `0 1 0` | `7 4 3` |
| `P1` | `3 2 2` | `3 0 2` | `0 2 0` |
| `P2` | `9 0 2` | `3 0 2` | `6 0 0` |
| `P3` | `2 2 2` | `2 1 1` | `0 1 1` |
| `P4` | `4 3 3` | `0 0 2` | `4 3 1` |

`Available` 用总量减去各列 `Allocation` 之和：

- 各列求和：`A: 0+3+3+2+0 = 8`，`B: 1+0+0+1+0 = 2`，`C: 0+2+2+1+2 = 7`
- `Available = (9-8, 3-2, 9-7) = (1, 1, 2)`

**校验**：`Available + 所有 Allocation` 应等于总量 `(1+8, 1+2, 2+7) = (9, 3, 9)` ✓

**第 2 问：安全性检查**

按五步算法，令 `Work = Available = (1, 1, 2)`：

| 步骤 | 检查 `Need <= Work` | 选中的进程 | `Work = Work + Allocation` | `Finish` |
| --- | --- | --- | --- | --- |
| 初始 | — | — | `Work = (1, 1, 2)` | 全 `false` |
| 1 | `P0` 需 `(7,4,3)` ✗；`P1` 需 `(0,2,0)` ✗（`B` 要 `2` 而只有 `1`）；`P2` 需 `(6,0,0)` ✗；`P3` 需 `(0,1,1)` ✓ | `P3` | `Work = (1,1,2) + (2,1,1) = (3, 2, 3)` | `P3 = true` |
| 2 | `P0` 需 `(7,4,3)` ✗；`P1` 需 `(0,2,0)` ✓ | `P1` | `Work = (3,2,3) + (3,0,2) = (6, 2, 5)` | `P1 = true` |
| 3 | `P4` 需 `(4,3,1)` ✗（`B` 要 `3` 而只有 `2`）；`P2` 需 `(6,0,0)` ✓ | `P2` | `Work = (6,2,5) + (3,0,2) = (9, 2, 7)` | `P2 = true` |
| 4 | `P4` 需 `(4,3,1)` ✗（`B` 仍只有 `2`）；`P0` 需 `(7,4,3)` ✓ | `P0` | `Work = (9,2,7) + (0,1,0) = (9, 3, 7)` | `P0 = true` |
| 5 | `P4` 需 `(4,3,1)` ✓（`B` 有 `3` 了） | `P4` | `Work = (9,3,7) + (0,0,2) = (9, 3, 9)` | `P4 = true` |

所有 `Finish` 均为 `true` ⇒ **`T0` 时刻系统处于安全状态**。

**一条安全序列**：`P3 → P1 → P2 → P0 → P4`

> 校验一下 `Available` 演进：`(1,1,2) + Alloc(P3) = (3,2,3)`；`+ Alloc(P1) = (6,2,5)`；`+ Alloc(P2) = (9,2,7)`；`+ Alloc(P0) = (9,3,7)`；`+ Alloc(P4) = (9,3,9)` = 总量 ✓。安全序列可能不唯一，写出任意一条并核对每一步即可。

**第 3 问：`Request1 = (1, 0, 2)` 能否分配**

按四步判断流程：

1. `Request1 <= Need1`？`(1,0,2)` 与 `P1` 的 `Need (0,2,0)` 比较：第 1 项 `1 > 0` ⇒ **不满足**！

也就是说，`Request1 = (1,0,2)` **超过了 `P1` 的最大需求**（`P1` 的 `Max` 是 `(3,2,2)`，已分配 `(3,0,2)`，它根本不需要 `A`），**属于非法请求，直接拒绝**。

> 若按此出题，学生常会跳过第 1 步直接去做安全性检查，得出"安全、可以分配"的错误结论。**第 1 步 `Request <= Need` 是不可省略的关卡。**

**第 4 问：`Request2 = (0, 2, 0)` 能否分配**

1. `Request2 <= Need1`？`(0,2,0) <= (0,2,0)` ✓
2. `Request2 <= Available`？`Available = (1,1,2)`，第 2 项 `2 > 1` ⇒ **不满足**！
3. 结论：**当前可用资源不足（`B` 类资源只有 `1` 个），`P1` 必须等待**，系统状态**不做任何改变**。
4. 补充说明：等待并不意味着系统不安全——第 2 问已证明 `T0` 时刻存在安全序列，`P1` 只需等到有进程释放出 `B` 类资源（例如 `P3` 完成后释放 `1` 个 `B`）再重新提出请求。

**采分点与常见坑**

- **采分点 1**：先算 `Need = Max - Allocation` 与 `Available = 总量 - 各列 Allocation 之和`，并**写出占位说明**（哪一列怎么加的）。这是独立得分点。
- **采分点 2**：安全性检查必须**画出 `Work` 的演进表**，每一步写清"选中谁、为什么能选中（`Need <= Work`）、`Work` 更新成多少"。只写"存在安全序列"不给过程分。
- **采分点 3**：请求判断要**写出完整四步**（`Request <= Need`、`Request <= Available`、试探分配、安全性检查），漏掉第 1 步是常见硬伤。
- **采分点 4**：结论要写全"安全/不安全 + 安全序列（若有）+ 能否分配"。
- **常见坑 1**：`Work` 更新时写成 `Work = Work + Need` 或 `Work = Work + Max`。**只能加 `Allocation`**（进程完成后释放的是它已占有的资源）。
- **常见坑 2**：试探分配时忘记同步更新 `Need`（`Max` 不变，`Available`、`Allocation`、`Need` 三者都要改）。
- **常见坑 3**：看到"资源不足"就答"系统不安全"。**资源不足 ⇒ 请求必须等待，与安全状态是两回事**。
- **常见坑 4**：把银行家算法说成"死锁预防"。它属于**死锁避免**——不破坏四个必要条件，而是在运行时动态判断。
- **常见坑 5**：认为"不安全状态就是死锁"。不安全只是"**可能**死锁"，标准结论只有"安全状态一定不死锁"。

## 六、简便方法与易错口诀（速算 · 防错）

> 本节把本章能"省时间"和"防掉坑"的招集中在一处：二轮复习与考前只看这一节。每条都写清**适用条件**。

### 6.1 速算招式

| 场景 | 常规做法（慢/繁） | 简便做法（快/稳） | 为什么成立 / 适用条件 |
| --- | --- | --- | --- |
| 周转三指标一条链 | 逐句读题、边读边推时间轴 | 先默写三条：`周转时间 = 完成时间 − 到达时间`、`带权周转时间 = 周转时间 ÷ 运行（服务）时间`、`等待时间 = 周转时间 − 运行时间`，再逐进程填表 | 三条都是定义式的直接变形，互不依赖。**适用条件**：`等待时间` 这条只在**不计 `I/O` 时间**时成立；题目给了 `I/O` 时间还要再减 `I/O` 时间（见下方订正提示） |
| 调度大题流程 | 在心里反复推演"谁先谁后" | 先画**甘特图**（一条时间轴标出各进程的占用区间），再照图逐行填"到达 / 运行 / 开始 / 完成 / 周转 / 带权"表 | 甘特图一次画清"顺序"与"时刻"，填表退化成抄图。**适用条件**：`FCFS`、`SJF`、`SRTN`、`HRRN`、`RR` 全部通用 |
| 抢占性速判 | 背每个算法的长篇优缺点 | 对号入座：`FCFS` 非抢占；`SJF` 有非抢占与抢占（`SRTN`）两版；`HRRN` 非抢占；`RR` 天然抢占；优先级调度**两者皆有** | 判据只有一个——**运行中的进程会不会在没跑完时被换下**。题干问"是否抢占"照此逐项对照即可 |
| `RR` 时间片设定 | 死记"`q` 要适中" | `q` 必须**远大于**一次上下文切换开销，同时**略大于**一次典型交互所需时间；`q` 太大退化成 `FCFS`，太小则 `CPU` 都耗在切换上 | 切换开销是纯开销、不产生价值，只有 `q` 远大于它，切换占比才可忽略；而 `q` 又不能大到让交互等太久。**适用条件**：题目给"切换时间"时，可用 `切换开销 ÷ q` 估切换占比 |
| `MLFQ` 方向记忆 | 背四条规则还常记反 | 记"**越往下，优先级越低、时间片越长**"（常按 2 倍递增）。再配三句：新进程进最高级；**用完时间片**没跑完 ⇒ 降级；**因 `I/O` 主动放弃** ⇒ 留在原级；被高优先级抢占 ⇒ 回**原队列末尾** | 方向记成"下 = 低优先级 + 长时间片"，就不会把降级写成升级；"`I/O` 型不降级"正是它兼顾短作业响应与长作业不饿死的关键 |
| `P`/`V` 初值速记 | 每题从头推一遍初值 | 三句话：**互斥**信号量初值 `1`；**资源 / 同步**信号量初值 = 资源数（缓冲区 `n` 个 ⇒ `empty = n`、`full = 0`）；**前驱关系**信号量初值 `0` | 初值 = "一开始手里有多少张凭证"：锁只有 1 把 ⇒ `1`；空位一开始全空 ⇒ `n`；产品一开始没有 ⇒ `0`；前驱事件一开始未发生 ⇒ `0` |
| `P` 操作顺序防死锁 | 随手写，写完才发现互相等 | 铁律：**先 `P` 资源信号量，再 `P` 互斥信号量**；`V` 的顺序无所谓 | 若先 `P(mutex)` 再 `P(empty)`：缓冲区满时生产者**抱着锁等空位**，消费者进不了临界区去释放空位 ⇒ 循环等待。`V` 只释放 / 唤醒、不会阻塞自己，所以顺序无关 |
| 银行家算法手算 | 每步重推各数据结构的含义 | 口诀：`Need = Max − Allocation`；在 `Finish == false` 的行里找 `Need <= Work`（**逐项**都满足），找到就 `Work = Work + Allocation`、置 `Finish = true`，再从头找；全部找完 ⇒ 安全 | `Work` 是"此刻系统还能动的资源"，进程跑完会把它**已占有的**还回来，故加 `Allocation` 而不是 `Need`。**适用条件**：`Finish` 全为 `true` 才是安全序列，只找到一部分不算。**不安全 ≠ 已死锁** |
| 死锁预防简答 | 写一大段原理 | 背四条件（**互斥、不可剥夺、请求并保持、循环等待**）+ 一句结论：破坏其中任意一条即可**预防**死锁；实际常破坏后三条，其中**顺序资源分配法**代价最小 | 四条件是"同时成立才可能死锁"的前提，破坏一条即链条断裂。**适用条件**：互斥条件通常破坏不了（打印机等本就独占），若答"破坏互斥"须补一句局限性 |
| 死锁 / 饥饿 / 死循环辨析 | 逐题回忆定义 | 三个关键词：死锁 = **互相等**且**至少两个进程**、都不占 `CPU`；饥饿 = **一直轮不到**（可只有 1 个进程、无环、可能占 `CPU`）；死循环 = **程序逻辑**错误，一直在跑、占 `CPU`、与资源无关 | 死锁必然导致相关进程饥饿，饥饿不一定是死锁；死循环与资源分配无关，不属同步互斥的范畴 |
| `HRRN` 响应比 | 记成"周转 ÷ 服务" | 记成 `响应比 = 1 + 等待时间 ÷ 要求服务时间`；等待越久、要求服务时间越短，响应比越高 | 展开即 `(等待时间 + 要求服务时间) ÷ 要求服务时间`。**适用条件**：`HRRN` **非抢占**，只在当前进程**完成后**才重新计算所有候选者 |
| 资源分配图判死锁 | 一上来就逐个试推 | 先看实例个数：**每类资源单实例** ⇒ **有环 ⇔ 死锁**；**某类资源多实例** ⇒ **有环只是必要条件**，必须做"化简"（能消去全部边才无死锁） | 单实例时环上每个进程都在等那唯一的实例，谁都推进不了；多实例时环上进程可能从同类空闲实例得到满足而脱环 |
| 结果自检 | 算完立刻交卷 | 两项体检：`带权周转时间 >= 1`（小于 `1` 必错）；银行家算法中每行 `Allocation + Need = Max`、每列 `Available + ΣAllocation = 资源总数` | 带权周转时间无量纲、恒 `>= 1`（等号仅当一到就跑完）；`Allocation` 与 `Need` 相加必回到 `Max`，可用来查表填错 |

> **订正提示（两处容易被"简便说法"带偏）**
>
> 1. 常被简写成万能式的 `等待时间 = 周转时间 − 运行时间`，严格写法是 **`等待时间 = 周转时间 − 运行时间 − I/O 时间`**：被 `I/O` 阻塞的时间不算"在就绪队列里干等"。题目不给 `I/O` 时间时两式等价。
> 2. `RR` 的时间片常被简写成"略大于上下文切换开销"。准确说法是 **`q` 必须远大于一次切换开销**（"略大于"容易被理解成只多一点点，那样切换占比会高得离谱）；同时 `q` 应**略大于一次典型交互所需时间**。两句一起记才不丢分。

### 6.2 口诀与记忆钩子

- **口诀**：三指标一条链——**完成减到达得周转，周转除运行得带权，带权不小于一**；等待时间要记得**扣掉 `I/O` 时间**。
- **口诀**：抢占性对号入座——"**`FCFS` 不抢，`SJF` 两版（`SRTN` 抢），`HRRN` 不抢，`RR` 必抢，优先级两可**"。
- **口诀**：`MLFQ` 记"**上小下大**"——越往下优先级越低、时间片越长；行为记"**用完降级、`I/O` 留级、被抢回尾**"。
- **口诀**：信号量初值记"**互斥一，资源数，前驱零**"；`P` 操作记"**先资源、后互斥，`V` 随便排**"。
- **口诀**：银行家算法记"**先算 `Need`，再找做得完的，做完把它占的还回来**"；"**全做完才叫安全，不安全不等于死锁**"。
- **口诀**：死锁四条件记"**互、不、请、循**"——互斥、不可剥夺、请求并保持、循环等待，破一条即预防。
- **口诀**：死锁 / 饥饿 / 死循环记"**死锁互相等，饥饿轮不到，死循环停不下**"（死锁至少两个进程，死循环与资源无关）。
- **口诀**：状态转换记"**阻塞只能被唤醒到就绪，就绪只能被调度到运行**"（所以"运行 → 阻塞"一步到位，"就绪 → 阻塞"不存在）。
- **口诀**：资源分配图记"**单实例有环即死锁，多实例有环未必死，化简到底才算数**"。

`P`/`V` 顺序的标准骨架（把顺序背成肌肉记忆）：

```c
/* 生产者：先 P 资源信号量（empty），再 P 互斥信号量（mutex） */
P(empty);   /* 没有空位就在这里等，此时手里不握锁 */
P(mutex);   /* 确认能进临界区了才加锁 */
    put(item);          /* 临界区 */
V(mutex);
V(full);    /* V 的顺序无所谓：只释放/唤醒，不会阻塞自己 */

/* ❌ 反例：先 P(mutex) 再 P(empty)
   缓冲区满时生产者抱着锁等空位，
   消费者进不了临界区去释放空位 ⇒ 互相等待（死锁） */
```

### 6.3 反例黑名单（这些"简便法"是错的）

- ❌ "`RR` 的时间片越小响应越快，所以越小越好"：正确做法是 `q` **略大于一次典型交互所需时间**且**远大于一次切换开销**；太小会让 `CPU` 大量耗在上下文切换上。
- ❌ "`等待时间 = 周转时间 − 运行时间` 万能"：正确做法是题目给了 `I/O` 时间时**再减 `I/O` 时间**，被 `I/O` 阻塞不算等待。
- ❌ "银行家算法里写 `Work = Work + Need`"：正确做法是 **`Work = Work + Allocation`**，且每一步 `Work` 的变化都要写出来（采分点）。
- ❌ "不安全状态就是死锁"：正确做法是"**不安全 ≠ 死锁**，只能说**可能**死锁；死锁 ⊆ 不安全状态"。
- ❌ "`MLFQ` 中进程一旦放弃 `CPU` 就降级"：正确做法是**因 `I/O` 主动放弃不降级**（留在原队列），只有**用完时间片**才降级。
- ❌ "先 `P(mutex)` 再 `P(empty)` 也没事"：正确做法是**先 `P` 资源信号量、再 `P` 互斥信号量**，否则缓冲区满时会死锁。
- ❌ "资源分配图里有环就是死锁"：正确做法是**每类资源单实例**时有环 ⇔ 死锁；**多实例**时须做化简，能消去全部边才无死锁。
- ❌ "`HRRN` 可以抢占、`SRTN` 是非抢占"：正确做法是 `HRRN` **非抢占**，`SRTN` 是 `SJF` 的**抢占**版本。
- ❌ "死锁是某个进程自己卡住了，一个进程也能死锁"：正确做法是死锁**至少两个进程**且**互相等待**；单进程谈不上死锁（那可能是死循环或饥饿）。
