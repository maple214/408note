## 一、本章知识框架

应用层是体系结构的最高层，也是**唯一直接面向用户**的一层。它不关心下面怎么传，只定义"进程之间怎么对话"。

```
应用层（第 6 章）
├── 网络应用模型
│   ├── C/S 模型（客户/服务器）
│   └── P2P 模型（对等）
├── DNS 系统（域名 → IP）
│   ├── 层次域名空间（根 → 顶级 → 二级 → 主机）
│   ├── 域名服务器（根 / 顶级 / 权限 / 本地）
│   └── 域名解析过程（递归 / 迭代 + 高速缓存）
├── FTP（文件传输）
│   ├── 工作原理（C/S、带外控制）
│   └── 控制连接 21 / 数据连接 20
├── 电子邮件
│   ├── 组成结构（用户代理 + 邮件服务器 + 协议）
│   ├── 邮件格式与 MIME
│   └── SMTP（推，25）/ POP3（拉，110）/ IMAP
└── WWW（万维网）
    ├── 概念与组成（URL + HTTP + HTML + 浏览器/服务器）
    └── HTTP 协议
        ├── 报文格式（请求/响应、方法、状态码）
        ├── 持久连接 / 非持久连接（RTT 计算）
        ├── Cookie 与 Web 缓存（代理服务器）
        └── HTTP/1.1 与 HTTP/2
```

**一条记忆主线（贯穿全章）**：`DNS` 把域名换成 `IP` → `TCP` 三次握手建连接 → `HTTP` 请求/响应拿页面 → 四次挥手释放；而 `FTP`、`SMTP`、`POP3`、`HTTP` 只是"应用层协议不同"，下面全都靠 `TCP`（`DNS` 查询靠 `UDP`）。

## 二、概念详解

### 6.1 网络应用模型

#### 6.1.1 客户/服务器（`C/S`）模型

**为什么会有它**：最早的网络应用（文件传输、邮件、网页）需要一个"永远在线、有固定地址"的一方来集中存放数据，另一方按需索取，于是自然形成"服务器被动等、客户主动求"的结构。

**核心特征**：

- 角色固定：`服务器` 是服务提供者，`客户` 是服务请求者。
- 服务器特点：**总是打开**、有**固定 IP 与固定端口**（如 Web 服务器 80）、可同时处理多个客户的请求。
- 客户特点：主动发起通信、不必有固定 IP、客户之间**不直接通信**。
- 通信是"请求—响应"式，由客户发起。

**优点**：集中管理、易于维护与安全控制、资源统一。
**缺点**：服务器压力随用户数线性增长，**可扩展性差**；服务器故障会导致整个应用瘫痪。

> **408 怎么考/常见坑**：判断题常问"客户之间可以直接通信吗"——不能，必须经服务器转发；"服务器必须知道客户的 IP 吗"——`TCP` 连接建立后当然知道，但服务器**不预先知道**、也不需要客户有固定 IP。端口号题要记住服务器端口是**熟知端口**。

#### 6.1.2 对等（`P2P`）模型

**为什么会有它**：当用户规模大到 `C/S` 服务器扛不住（如大文件分发），人们发现"每个下载者手里已经有了一部分数据"，于是让**每个节点既是客户又是服务器**，把带宽压力从中心摊到全体。

**核心特征**：

- 没有固定的服务请求者/提供者之分，每个对等方（peer）**既请求服务也提供服务**。
- 节点可以动态加入、随时离开，具有**自扩展性（可扩展性好）**。
- 典型代表：`BitTorrent`（比特洪流）——把文件切成很多小块，节点互相交换"稀缺块优先"，并用"一报还一报（tit-for-tat）"的策略激励上传。

> **408 怎么考/常见坑**：`P2P` 的考点几乎只考"特点对比 + 可扩展性"，不会考 `BitTorrent` 的具体算法细节。陷阱说法："`P2P` 中不存在服务器"——错，`P2P` 通常仍有**索引/追踪服务器（tracker）**帮助节点互相发现，只是数据不经过服务器。

### 6.2 `DNS` 系统

**为什么需要 `DNS`**：人记不住 `142.250.72.14` 这种 `IP`，但路由器只认 `IP`。所以需要一套"名字 → `IP`"的分布式数据库，这就是 `DNS`（域名系统）。它是**分布式**的，因为全球域名数量太大，集中存储既不可靠也不可扩展。

#### 6.2.1 层次域名空间

域名结构形如：`主机名.三级域名.二级域名.顶级域名`，例如 `www.cs.pku.edu.cn`。

| 级别 | 例子 | 说明 |
|---|---|---|
| 根 | `.` | 最上层，用点表示 |
| 顶级域名（`TLD`） | `cn`、`com`、`edu`、`org` | 分国家顶级域名（如 `cn`、`us`）与通用顶级域名（如 `com`、`edu`、`gov`） |
| 二级域名 | `pku`、`cs` | 由顶级域名管理机构下放给单位 |
| 主机名 | `www` | 具体主机 |

**关键点（必考）**：域名**级别从左到右依次降低**，即最右边是最高级。写作 `www.cs.pku.edu.cn` 时，`.cn` 级别最高，`www` 最低。

- 域名**不区分大小写**。
- 一个域名只能对应一个主机？——错，**多台主机可以共用一个域名**（配合负载均衡），用 `CNAME` 也能做别名。
- 域名与 `IP` 不是一对一：一个 `IP` 可对应多个域名，一个域名也可（在不同时刻）对应不同 `IP`。

> **408 怎么考/常见坑**：常考"以下域名中级别最高的是"——选最**右侧**的顶级域名。别把 `www.cs.pku.edu.cn` 的 `www` 当成"最高级"。

#### 6.2.2 域名服务器

`DNS` 采用分布式层次数据库，对应四类服务器：

| 服务器 | 作用 | 掌握要点 |
|---|---|---|
| 根域名服务器 | 知道所有顶级域名服务器的 `IP` | 全球共 13 组（逻辑上 13 个），最重要 |
| 顶级域名服务器 | 管理该顶级域名下的所有二级域名 | 如 `cn` 服务器 |
| 权限域名服务器（权威） | 管理某个区（zone）内的域名 | 保存最终答案，是"权威"来源 |
| 本地域名服务器（默认） | 主机首先询问的对象 | 通常由 `ISP` 或单位提供，**不属于层次结构**，起代理作用 |

**层次关系**：根 → 顶级 → 权限，逐级下降；本地域名服务器是主机与这套层次之间的"中间人"。
**区的概念**：一台权限域名服务器负责的范围叫"区"，一个区可以小于一个域（把大域拆成几个区，各设权限服务器）。

> **408 怎么考/常见坑**：常考"本地域名服务器是否属于层次结构"——**不属于**；"根域名服务器知道所有域名吗"——不知道，它只知道顶级域名服务器的地址。

#### 6.2.3 域名解析过程

主机 → 本地域名服务器 →（若缓存未命中）→ 根 → 顶级 → 权限。

主机的查询请求：一般先查**本机 `DNS` 高速缓存**（含 hosts 文件记录），未命中再发查询。

**递归查询 vs 迭代查询**：

- **递归查询**：被询问者"负责到底"，替你继续问别人，最后把答案给你。主机向本地域名服务器的查询**通常用递归**。
- **迭代查询**：被询问者只回答"你下一步该问谁"，不替你问。本地域名服务器向根/顶级/权限的查询**通常用迭代**。

**时延计算（`RTT` 计法）**：

- 本地域名服务器**无缓存**、采用迭代查询时，需要访问：根、顶级、权限共 **3 次**查询，加主机→本地 1 次，共约 **4 个 `RTT`**。
- 若本地服务器缓存了权限服务器的记录，则可能只需 **1 个 `RTT`**（主机→本地）。
- 若主机本身有缓存，则 **0 个 `RTT`**。
- 注意：每个 `RTT` 指的是"一次请求 + 一次应答"的往返时间；题目若给出"各级服务器处理时间"要另加。

**高速缓存的作用**：把最近查询过的"域名—`IP`"映射存在本地（主机或本地域名服务器），并设置**生存时间 `TTL`**；作用是大**减少网络上的 `DNS` 查询流量、降低解析时延**。缓存是"有代价的"——`TTL` 到期前若 `IP` 变了，会短暂解析到旧地址。

**`DNS` 记录类型**：

| 类型 | 含义 | 例子 |
|---|---|---|
| `A` | 主机名 → `IPv4` 地址 | `www.pku.edu.cn` → `A` → `162.105.x.x` |
| `AAAA` | 主机名 → `IPv6` 地址 | 概念性了解 |
| `CNAME` | 别名 → 规范名 | `www` → `CNAME` → `server1.pku.edu.cn` |
| `MX` | 邮件服务器记录 | 指向该域的邮件服务器 |
| `NS` | 该域的权限域名服务器 | 说明"这个域由谁管" |

**`UDP` 53 与 `TCP` 53**：

- **查询/应答用 `UDP` 53**：报文短、开销小、快，一次一问一答，丢了自己重传即可。
- **区域传送用 `TCP` 53**：主从域名服务器之间同步整块数据，数据量大且要求可靠，故用 `TCP`。

> **408 怎么考/常见坑**：① 给一张查询图问"哪几步是递归、哪几步是迭代"——记住"主机→本地=递归，本地→根/顶级/权限=迭代"。② 算 `RTT` 时不要漏掉最开始的"主机→本地"那一次。③ `DNS` 端口 53，既用 `UDP` 又用 `TCP`，别只记一个。④ `DNS` 服务器之间的"区域传送"属于 `TCP`，是高频细节题。

### 6.3 `FTP`

**为什么需要两条连接**：`FTP` 的传输可能要持续很久，而用户中途需要"暂停、改目录、换文件"。如果控制信息和数据挤在一条连接上，大数据会把控制命令堵住。于是 `FTP` 把**控制信息与数据分开传**，这叫**带外控制（out-of-band control）**。

**工作原理**：

- `FTP` 采用 `C/S` 方式；服务器进程由**主进程**（监听 21）和若干**从属进程**（负责具体传输）组成。
- **控制连接**：服务器端口 **21**，**在整个会话期间一直保持**，传的是命令与应答（`USER`、`PASS`、`RETR`、`STOR`、`QUIT` 等），`7` 位 `ASCII`。
- **数据连接**：服务器端口 **20**，**每传一次文件就建立、传完即关闭**（非持续）。
- 两个连接都基于 `TCP`。

**两种数据连接建立方式**：

- **`PORT`（主动模式）**：客户用某个临时端口 `N` 监听，通过控制连接把 `N` 告诉服务器；服务器从**自己的 20 端口**主动连接客户的 `N`。缺点是客户若在防火墙/NAT 后会被挡。
- **`PASV`（被动模式）**：客户发 `PASV`，服务器开一个临时端口并告知客户，客户主动去连服务器。对客户端更友好。

**传输模式**：`ASCII` 模式（文本，会做换行转换）与二进制模式（`binary`，如图片、压缩包，不做任何转换）。传可执行文件必须用二进制，否则文件会损坏。

**`FTP` 与 `HTTP` 对比**：

| 对比项 | `FTP` | `HTTP` |
|---|---|---|
| 连接数 | 控制连接 + 数据连接，**两条** | 只有一条 `TCP` 连接 |
| 状态保持 | 控制连接保持会话状态（记住当前目录、登录身份） | `HTTP` 本身**无状态**（靠 `Cookie` 补） |
| 数据连接方向 | 可主动（`PORT`）或被动（`PASV`） | 由客户发起 |
| 默认端口 | 21（控制）/ 20（数据） | 80（`HTTP`）/ 443（`HTTPS`） |
| 传输内容 | 文件 | 主要是超文本/资源 |

> **408 怎么考/常见坑**：① "控制连接一直保持、数据连接传完就断"是必背。② 端口别记反：**21 控制、20 数据**（20 是"数据"更顺口）。③ `FTP` 是**有状态**的（记住登录与目录），`HTTP` 是**无状态**的——易错点。④ `FTP` 使用 `TCP`，不是 `UDP`。

### 6.4 电子邮件

#### 6.4.1 系统组成结构

| 组成部分 | 作用 |
|---|---|
| 用户代理（`UA`） | 用户与邮件系统交互的软件（`Outlook`、网页邮箱），负责撰写、显示、收发 |
| 邮件服务器 | 真正的"邮局"：发送方服务器（`SMTP` 客户）与接收方服务器（`SMTP` 服务器），负责投递与暂存 |
| 协议 | 发送/中继用 `SMTP`，读取用 `POP3` 或 `IMAP` |

**一封信的旅行**：发件人 `UA` →（`SMTP`，推）→ 发送方邮件服务器 →（`SMTP`，推）→ 接收方邮件服务器 →（`POP3`/`IMAP`，拉）→ 收件人 `UA`。

> **408 怎么考/常见坑**：`SMTP` 只负责"把邮件推出去"，`POP3` 只负责"把邮件拉下来"。**发送与读取用的是不同协议、不同方向**，这是本章最经典的混淆点。

#### 6.4.2 电子邮件格式与 `MIME`

**邮件格式**（`RFC 822`）：分**首部（header）**与**正文（body）**，中间空一行。

常见首部字段：`From`（发件人）、`To`（收件人）、`Subject`（主题）、`Cc`（抄送）、`Date`、`Message-ID`。

**`MIME` 为什么出现**：`SMTP` 只能传 **7 位 `ASCII`** 码（早期网络的限制），但用户要发图片、音频、中文、附件。`MIME`（多用途互联网邮件扩展）**不是新协议**，而是对 `SMTP` 的**扩展**：在发送前把非 `ASCII` 数据**编码成 7 位 `ASCII` 形式**，接收端再解码还原。

`MIME` 新增的首部字段：`MIME-Version`、`Content-Type`（如 `text/html`、`image/jpeg`）、`Content-Transfer-Encoding`（如 `base64`、`quoted-printable`）、`Content-Description`。

> **408 怎么考/常见坑**：① "`MIME` 是一种邮件传输协议"——**错**，它是编码/扩展规范。② "`SMTP` 能直接传二进制"——错，必须经 `MIME` 编码。③ `base64` 会把数据长度变大约 1/3，这是编码代价。

#### 6.4.3 `SMTP` 与 `POP3`

**`SMTP`（简单邮件传输协议）**：

- 作用：**推（push）**，把邮件从 `UA` 推到服务器、或从服务器推到服务器。
- 端口：**25**（`TCP`）；可靠传输。
- 命令/应答：`ASCII` 文本，如 `HELO`、`MAIL FROM`、`RCPT TO`、`DATA`、`QUIT`，应答如 `250 OK`。
- 局限：只能传 7 位 `ASCII`（靠 `MIME` 补）。

**`POP3`（邮局协议第 3 版）**：

- 作用：**拉（pull）**，把邮件从接收方服务器下载到本地 `UA`。
- 端口：**110**（`TCP`）。
- 两种工作方式：
  - **下载并删除**：邮件下到本地后服务器删除 → 换设备就看不到旧邮件，但节省服务器空间。
  - **下载并保留**：服务器仍保留副本 → 多设备可看，但占空间、且各设备状态不同步。
- 特点：`POP3` 在下载过程中**基本不维护跨会话状态**，功能简单。

**`IMAP`（互联网报文存取协议）**：

- 端口 **143**（`TCP`）。
- 特点：**所有邮件保存在服务器**，用户代理与服务器**双向同步**（已读/未读、文件夹、草稿都在服务器），适合多设备。
- 概念性了解即可：比 `POP3` 复杂、功能强。

> **408 怎么考/常见坑**：端口必须背熟：`SMTP`=25、`POP3`=110、`IMAP`=143。方向题："从邮件服务器读取邮件用什么协议"——`POP3`/`IMAP`，不是 `SMTP`。另外 `SMTP` 也可以用于"服务器→服务器"的中继，不要以为只有 `UA` 才能用。

### 6.5 `WWW`

#### 6.5.1 `WWW` 的概念与组成结构

`WWW`（万维网）是一个**分布式超媒体系统**，用**超链接**把分布在全球的文档连起来。

四个组成部分：

| 组成 | 说明 |
|---|---|
| `URL`（统一资源定位符） | 给每个资源一个全球唯一的名字 |
| `HTTP`（超文本传输协议） | 规定浏览器与服务器怎么对话 |
| `HTML`（超文本标记语言） | 描述页面结构与超链接 |
| 浏览器 + `Web` 服务器 | 客户进程与服务器进程 |

`WWW` 采用 `C/S` 工作方式；浏览器是客户，`Web` 服务器是服务器。

**`URL` 的组成**：`<协议>://<主机>:<端口>/<路径>`

例如 `http://www.pku.edu.cn:80/cs/index.html`

- `<协议>`：`http`、`https`、`ftp`
- `<主机>`：域名或 `IP`（必填）
- `<端口>`：可省略，省略时用协议默认端口（`http` 80、`https` 443）
- `<路径>`：可省略，省略时通常是 `index.html`

> **408 怎么考/常见坑**：问"`URL` 中哪部分不可省略"——**主机（域名/IP）不可省略**。注意 `https` 默认 443、`http` 默认 80。

#### 6.5.2 `HTTP` 协议与报文格式

**`HTTP` 的特点**：

- 使用 `TCP`（80 端口），**无状态**、**无连接**（指"不保存连接状态"，不是说不用 `TCP`）。
- `HTTP` 本身不保存任何客户信息 → 需要 `Cookie` 来"续状态"。

**请求报文**（`HTTP` 请求）：结构为 **请求行 + 首部行 + 空行 + 实体主体**。

```
GET /index.html HTTP/1.1        ← 请求行：方法 URL 版本
Host: www.pku.edu.cn            ← 首部行
User-Agent: Mozilla/5.0
Connection: close               ← 非持久连接
Accept-Language: zh-CN
                                ← 空行
（GET 一般无实体主体）           ← 实体主体
```

**响应报文**：**状态行 + 首部行 + 空行 + 实体主体**。

```
HTTP/1.1 200 OK                 ← 状态行：版本 状态码 短语
Server: nginx
Content-Type: text/html
Content-Length: 1024
                                ← 空行
<html>...</html>                ← 实体主体（页面内容）
```

**常见方法**：

| 方法 | 含义 | 有无实体主体 |
|---|---|---|
| `GET` | 请求读取资源 | 通常无 |
| `HEAD` | 只要首部，不要主体（用于检查资源是否存在/是否更新） | 无 |
| `POST` | 向服务器提交数据 | 有 |
| `PUT` | 上传/替换资源 | 有 |
| `DELETE` | 删除资源 | 无 |

**状态码分类与高频码**：

| 类别 | 含义 | 常见码 |
|---|---|---|
| `1xx` | 通知信息（中间状态） | — |
| `2xx` | 成功 | `200 OK`（请求成功） |
| `3xx` | 重定向 | `301`（永久移动）、`304`（资源未修改，用缓存） |
| `4xx` | 客户错误 | `404 Not Found`（资源不存在） |
| `5xx` | 服务器错误 | `500 Internal Server Error` |

> **408 怎么考/常见坑**：状态码首数字的含义必记；`304` 与 `Cache-Control`/`If-Modified-Since` 常一起考"缓存是否可用"。请求行与状态行的顺序别写反（请求行是"方法在前"，状态行是"版本在前"）。

#### 6.5.3 持久连接与非持久连接

**非持久连接（`HTTP/1.0`）**：**每个对象（每个 `URL`）都要新建一条 `TCP` 连接**，取完就关。

- 缺点：每个对象都要一次 `TCP` 三次握手，服务器负担重、时延大。

**持久连接（`HTTP/1.1` 默认）**：`TCP` 连接建立后可**连续传多个对象**，最后才关闭。

- **流水线（pipelining）方式**：客户可以**连续发出多个请求**，不必等前一个响应回来 → 理想情况下所有对象总共只需 **1 个 `RTT`**（不含连接建立）。
- **非流水线方式**：客户**每发一个请求必须等响应回来**才能发下一个 → 每个对象各需 1 个 `RTT`。

**`RTT` 计算模型（重点）**：

- 记 `RTT` 为一次往返时间，**三次握手 = 1 个 `RTT`**（前两次握手占 1 个 `RTT`，第三次与请求"捎带"可忽略）。
- **非持久连接**：第 1 个对象需 `2 RTT`（1 个握手 + 1 个请求响应），之后每个对象再加 `2 RTT`
  → 总时延 = `2n × RTT`（`n` 为对象数）。
- **持久连接 + 非流水线**：握手 1 次（`1 RTT`），之后每个对象各 `1 RTT`
  → 总时延 = `(n + 1) × RTT`。
- **持久连接 + 流水线**：握手 1 次，所有请求连续发出，响应连续回来
  → 总时延 ≈ `2 × RTT`（1 个握手 + 1 个"请求—响应"往返），与对象数几乎无关。
- 若题目给出"传输时延/发送时延"，要在 `RTT` 基础上**另加**，并注意串行/并行的带宽分配。

> **408 怎么考/常见坑**：这类题几乎每年都有变体，核心是分清"建连接算不算 RTT"和"对象是一个个来还是一起发"。常见坑：把三次握手算成 `1.5` 个或 `3` 个 `RTT`；忘记第一个对象和后续对象时延不同；题目说"采用持久连接、非流水线"却按流水线算。

#### 6.5.4 `Cookie`、`Web` 缓存与代理服务器

**`Cookie` 的作用与工作过程**：`HTTP` 无状态，服务器无法识别"你是同一个人"。`Cookie` 就是让服务器在**无状态的 `HTTP` 之上记住用户**的机制。

工作过程：

1. 用户首次访问某网站（如登录成功），服务器在响应报文中加 `Set-cookie: 用户ID` 首部。
2. 浏览器把该 `Cookie` 存到本地（按域名管理）。
3. 之后对该服务器的每个请求，浏览器都在请求头中加 `Cookie: 用户ID`。
4. 服务器读 `Cookie`，识别用户，实现会话保持（购物车、免登录等）。

**`Cookie` 与 `Session` 对比**：

| 对比项 | `Cookie` | `Session` |
|---|---|---|
| 存放位置 | 客户端（浏览器） | 服务器端 |
| 内容 | 明文可见，可被用户查看/篡改 | 服务器内存/数据库中的对象 |
| 安全性 | 较低 | 较高 |
| 联系 | `Session` 的标识（`SessionID`）通常**通过 `Cookie` 传给客户端**保存 | 同左 |
| 生命周期 | 可设过期时间，长期存在 | 会话结束或超时即失效 |

**`Web` 缓存（代理服务器）**：

- 代理服务器位于客户与源服务器之间，**保存最近请求过的对象的副本**。
- 命中时直接返回副本 → **减少响应时延、减少出口链路带宽占用、减轻源服务器负担**。
- 典型部署：校园网/企业出口部署代理服务器（如 `Squid`）。
- 条件 `GET`：客户发 `If-Modified-Since`，资源未变则服务器回 `304 Not Modified`（不传主体）。

> **408 怎么考/常见坑**：`Cookie` 是"客户端保存、服务器读取"；`Session` 是"服务器保存"。别把 `Cookie` 说成服务器端存储。代理服务器与"浏览器本地缓存"不是一回事：前者是**网络中的中间实体**，后者在客户本机。

#### 6.5.5 `HTTP/1.1` 与 `HTTP/2`（概念性区别）

| 对比项 | `HTTP/1.1` | `HTTP/2` |
|---|---|---|
| 连接复用 | 持久连接 + 可流水线，但存在**队头阻塞** | **多路复用**：一条 `TCP` 连接上并行交错传多个流 |
| 报文形式 | 文本（`ASCII`） | **二进制分帧**（`frame`），更易解析、更省带宽 |
| 首部压缩 | 无 | 有（`HPACK`） |
| 服务器推送 | 无 | 支持 `Server Push` |

一句话：`HTTP/2` 在 `HTTP/1.1` 语义不变的前提下，**用二进制分帧 + 多路复用**解决"文本 + 串行"带来的效率问题。

> **408 怎么考/常见坑**：通常只考"`HTTP/2` 的关键词：多路复用、二进制分帧"，不会深挖细节。注意 `HTTP/2` 仍然是"请求—响应"模型且仍然用 `TCP`（`HTTP/3` 才改用 `QUIC`/`UDP`）。

## 四、例题精练（3 道）

### 例题 1（选择题）

**题目**：关于 `DNS` 域名解析，下列说法中**正确**的是（　）。

A. 主机向本地域名服务器发送的查询通常是迭代查询
B. 本地域名服务器向根域名服务器发送的查询通常是递归查询
C. 域名解析过程中，若本地域名服务器的高速缓存中有该域名记录，则不必再向根域名服务器查询
D. `DNS` 只使用 `UDP` 进行传输，端口号为 53

**逐项解析**：

- **A 错**：方向记反了。主机→本地域名服务器用的是**递归查询**，本地域名服务器替主机问到底。
- **B 错**：本地域名服务器→根（以及顶级、权限）通常是**迭代查询**，根只告诉它"下一步该问哪个顶级域名服务器"。
- **C 对**：高速缓存中若已有该域名的"域名—`IP`"映射（且未过 `TTL`），本地服务器直接返回答案，可以省掉向根、顶级、权限的全部查询，这也是缓存能降低时延的原因。
- **D 错**：`DNS` 查询用 `UDP` 53，但**区域传送用 `TCP` 53**；当响应报文过长时也可能改用 `TCP`。

**答案：C**

**采分点与常见坑**：

- 采分点：区分"主机→本地（递归）"与"本地→根/顶级/权限（迭代）"；知道缓存的作用范围；记得 `DNS` 的 `UDP`/`TCP` 两种场合。
- 常见坑：把 A、B 两项说反；把 `DNS` 一口咬定为"只用 `UDP`"。

### 例题 2（综合题）

**题目**：某主机要访问 `www.example.com`。已知该主机与本地域名服务器之间、本地域名服务器与根/顶级/权限域名服务器之间，每次请求—应答的往返时间均为一个 `RTT`（各级服务器处理时间忽略不计，且主机的 `DNS` 缓存为空）。请回答：

（1）若本地域名服务器缓存为空，采用"主机→本地递归，本地→根/顶级/权限迭代"的方式，从开始解析到主机拿到 `IP` 共需多少个 `RTT`？写出每一步。
（2）若本地域名服务器的缓存中恰好有 `www.example.com` 的 `A` 记录（未过期），共需几个 `RTT`？
（3）若主机的本机缓存中就有该记录，需要几个 `RTT`？说明高速缓存的作用。
（4）题目中"本地域名服务器向根域名服务器发起查询"这一步，属于递归还是迭代？为什么这样设计？

**解答**：

（1）共需 **4 个 `RTT`**：

| 步骤 | 动作 | 累计 `RTT` |
|---|---|---|
| ① | 主机 → 本地域名服务器（递归查询） | 1 |
| ② | 本地 → 根域名服务器（迭代，得知顶级域名服务器地址） | 2 |
| ③ | 本地 → 顶级域名服务器（迭代，得知权限域名服务器地址） | 3 |
| ④ | 本地 → 权限域名服务器（迭代，得到最终 `IP`） | 4 |

（本地服务器把最终结果回给主机可视为递归查询的"响应"已在 ① 的等待中完成，题目按一次往返计。）

（2）只需 **1 个 `RTT`**：本地服务器直接命中缓存并返回结果，主机只做了一次"主机→本地"的请求—应答。

（3）需要 **0 个 `RTT`**（就"网络往返"而言）：主机查询本机缓存/hosts 即可直接得到 `IP`，不产生任何网络查询。

高速缓存的作用：把最近解析过的映射保存在主机或本地域名服务器中（配合 `TTL` 过期机制），**避免重复的 `DNS` 查询、减少 `DNS` 流量、显著降低解析时延**；代价是 `TTL` 内若 `IP` 变更，可能短暂解析到旧地址。

（4）属于**迭代查询**。因为根域名服务器是全球最繁忙的节点，如果让它对每个查询都"递归问到底"，负载会不可承受；迭代方式把"继续追问"的任务交给请求方（本地域名服务器），根只需回答"去问谁"，从而**分散负载、提高 `DNS` 的整体可扩展性**。

**采分点与常见坑**：

- 采分点：会画 ①②③④ 四步顺序；知道每步各花 1 个 `RTT`；能说清缓存命中后省掉的是哪几步。
- 常见坑：漏掉"主机→本地"这一次，答成 3 个 `RTT`；把本地→根说成递归；把缓存命中也算成 3 个 `RTT`。

### 例题 3（综合题）

**题目**：某网页 `index.html` 中引用了 **5 个**小图片（与主页在同一服务器上，且图片可以并行传输，忽略各对象的发送时延与服务器处理时间）。客户端到服务器的一次往返时间为 `RTT`。请分别计算下列三种情况下，从建立连接开始到**所有对象接收完毕**所需的 `RTT` 数，并比较优劣：

（1）`HTTP/1.0` 非持久连接；
（2）`HTTP/1.1` 持久连接、**非流水线**方式；
（3）`HTTP/1.1` 持久连接、**流水线**方式。

**解答**：对象总数 `n = 1`（主页）+ `5`（图片）= **6**。

（1）**非持久连接**：每个对象各自建立一条 `TCP` 连接，先 1 个 `RTT` 握手，再用 1 个 `RTT` 请求/响应 → 每个对象 `2 RTT`。

```
总时延 = 2n × RTT = 2 × 6 × RTT = 12 RTT
```

（2）**持久连接 + 非流水线**：只需第一次握手（`1 RTT`），之后每个对象各需 1 个 `RTT`。

```
总时延 = 1 RTT（握手）+ 6 × 1 RTT（每个对象）= 7 RTT
```

（3）**持久连接 + 流水线**：握手 `1 RTT`，然后 6 个请求连续发出、响应陆续返回。

```
总时延 = 1 RTT（握手）+ 1 RTT（第一批请求—响应往返）≈ 2 RTT
```

（理想化模型；若严格认为后方请求需等到响应到达后才发送，则近似为 `1 + 1 = 2 RTT`，仍是三者中最小。）

**比较**：`12 RTT` > `7 RTT` > `2 RTT`。

- 持久连接相比非持久连接，省掉了"为每个对象重复三次握手"的开销，且让 `TCP` 慢启动/拥塞控制在连接生命周期内只经历一次。
- 流水线相比非流水线，省掉了"每个对象都要等一个完整 `RTT`"的串行等待，因此效率最高。
- 但 `HTTP/1.1` 的流水线仍受**队头阻塞**影响，这也是 `HTTP/2` 引入**多路复用 + 二进制分帧**的动机。

**采分点与常见坑**：

- 采分点：正确数出对象个数（**别忘了主页本身**）；区分非持久 `2n`、持久非流水线 `n+1`、流水线约 `2`；能写出三个公式并比较。
- 常见坑：忘记把 `index.html` 计入对象，算成 `10`/`5` 个；把三次握手算成 `1.5` 或 `3` 个 `RTT`；对非持久连接每个对象只算 `1 RTT`（忘了握手）；题目已说明"图片可并行传输"时仍按串行叠加，需按题意处理并行部分。
- 若题目额外给出"单个对象发送时延"或"链路带宽"，要在上述 `RTT` 结果上**另加链路传输时延**，不要与 `RTT` 混在一起。

## 六、简便方法与易错口诀（速算 · 防错）

> 本节把本章能"省时间"和"防掉坑"的招集中在一处：二轮复习与考前只看这一节。每条都写清**适用条件**。

### 6.1 速算招式

| 场景 | 常规做法（慢/繁） | 简便做法（快/稳） | 为什么成立 / 适用条件 |
| --- | --- | --- | --- |
| 求 `HTTP` 取 `n` 个对象的总时延 | 一个对象一个对象画时序图累加 | 先判连接方式，再套公式：非持久 `2n × RTT`；持久非流水线 `(n + 1) × RTT`；持久 + 流水线 ≈ `2 × RTT` | 适用条件：忽略发送时延与服务器处理时间，`RTT` = 一次请求—应答往返；口径与本章例题 3 一致 |
| 数一共几个对象 | 只数页面里有几张图片 | 对象数 = 主页 `1` 个 + 每个引用资源 `1` 个 | 5 张图 → `n = 6`（不是 5）；漏数主页是本类题第一失分点 |
| 单个对象该算几个 `RTT` | 每次重新判断"握手算不算" | 非持久连接：**每个对象 `2 RTT`（握手 `1` + 请求/响应 `1`）**；持久非流水线：**连接建好后每个对象 `1 RTT`** | 前提是三次握手按 `1 RTT` 计（第 1、2 次握手占 `1 RTT`，第 3 次与请求捎带） |
| 算 `DNS` 解析的 `RTT` | 重画整棵查询树再数 | **数"问了几次"就够，每问一次 = `1 RTT`**：本地无缓存 + 迭代 = `4 RTT`（主机→本地 1 + 根/顶级/权限 3）；本地缓存命中 = `1 RTT`；主机缓存命中 = `0 RTT` | 适用条件：递归只发生在"主机→本地"这一跳，其余为迭代；题目若给"各级服务器处理时间"须另加 |
| 端口速查 | 逐个翻表找 | 背成三串：**21/20 · 25 · 53 · 67/68 · 80 · 110 · 143 · 443**（依次为 `FTP` 控制/数据、`SMTP`、`DNS`、`DHCP`、`HTTP`、`POP3`、`IMAP`、`HTTPS`） | `DHCP` 是 67（服务器）/ 68（客户端）；`DNS` 查询用 `UDP` 53、区域传送用 `TCP` 53 |
| 判断状态码类别 | 死记每个状态码 | 看首位数字：`1xx` 信息、`2xx` 成功、`3xx` 重定向、`4xx` 客户端错、`5xx` 服务器错；高频记 `200`、`301`、`304`、`404`、`500` | 首位数字即"责任方"：`4xx` 怪客户、`5xx` 怪服务器 |
| 判断"推"还是"拉" | 回忆完整收发邮件流程 | 主动把数据塞给对方 = 推（`SMTP` 25）；把数据取回自己这边 = 拉（`POP3` 110 / `IMAP` 143） | `SMTP` 也用于"服务器→服务器"中继；`IMAP` 是"拉 + 双向同步"，功能比 `POP3` 强 |
| 默写一次网页访问流程 | 从"输入网址"开始漫谈 | 固定六步：`DNS` 域名→`IP` → `ARP` `IP`→`MAC` → `TCP` 三次握手 → 发 `HTTP` 请求 → 收响应 → 四次挥手 | 注意 `DNS` 与 `ARP` 的先后要按"访问谁"判断，见 6.3 第 5 条 |
| 判断 `URL` 哪些部分能省 | 逐项分析每个字段 | 只有**主机（域名/`IP`）不可省**；协议默认 `http`、端口随协议取默认（`http` 80、`https` 443）、路径默认 `index.html` | 结构为 `<协议>://<主机>:<端口>/<路径>`；题目问"哪部分不可省略"就答主机 |
| 一句话说清 `MIME` | 记一串首部字段 | 把非 `ASCII` 数据编码成 `SMTP` 能传的 **7 位 `ASCII`** 形式 | 它不是协议，是 `SMTP` 的编码扩展；`base64` 会使数据长度约增大 `1/3`（编码代价） |

### 6.2 口诀与记忆钩子

- **口诀**：**握手占 `1` 个 `RTT`，请求—响应再占 `1` 个 `RTT`**——所以非持久连接每个对象 `2 RTT`（`2n`），持久非流水线建好连接后每个对象 `1 RTT`（`n + 1`），流水线一次发完约 `2 RTT`。
- **口诀**：**主机问本地用递归，本地问别人用迭代**（"主机偷懒、本地接力"）；配套数数：主机→本地 `1` 次 + 根/顶级/权限 `3` 次 = **`4` 个 `RTT`**。
- **口诀**：**发邮件推 `25`，收邮件拉 `110`/`143`，查域名 `53`（查询用 `UDP`、传送用 `TCP`）**。
- **口诀**：**状态码看首位：`1` 信息、`2` 成功、`3` 重定向、`4` 客户错、`5` 服务器错**（`404` 是"你"错了，`500` 是服务器错了）。
- **口诀**：**`FTP` 两条腿：`21` 管嘴（控制连接，全程不断）、`20` 管腿（数据连接，传完就断）**。
- **口诀**：**`Cookie` 在客户、`Session` 在服务器**（"饼干带在身上，会话存在店里"）。

### 6.3 反例黑名单（这些"简便法"是错的）

- ❌ **"非持久连接每个对象只算 `1` 个 `RTT`"**：正确做法是每个对象算 **`2` 个 `RTT`**（`1` 个握手 + `1` 个请求/响应）；只有连接已建好的持久连接才能按"每个对象 `1 RTT`"算。
- ❌ **"三次握手等于 `1.5` 或 `3` 个 `RTT`"**：正确做法是握手按 **`1` 个 `RTT`** 计（第 1、2 次握手构成 `1 RTT`，第 3 次与随后请求捎带，不再单独计时）。
- ❌ **"对象数只数页内图片"**：正确做法是把主页本身也算 `1` 个对象（5 张图 → `n = 6`），否则 `2n × RTT` 与 `(n + 1) × RTT` 全算错。
- ❌ **"本地域名服务器属于 `DNS` 层次结构 / `DNS` 只用 `UDP`"**：正确做法是本地域名服务器**不属于**层次结构（它起代理作用），且**区域传送用 `TCP` 53**、响应报文超过 512 字节时也可能改用 `TCP`。
- ❌ **"一定是先 `DNS` 拿 `IP`、再 `ARP` 拿 `MAC`"**：这个顺序只在"访问目标主机"这一层成立。订正：主机向本地域名服务器发查询时，若本地域名服务器不在同一网段，主机在封装这个 `DNS` 查询帧之前就**已经要先用 `ARP` 解析网关的 `MAC`**。正确表述是——**为解析域名可能先 `ARP` 找网关，拿到 `IP` 后再为访问该 `IP` 做 `ARP`（或沿用已缓存的网关 `MAC`）**。
- ❌ **"`MIME` 是一种邮件传输协议 / `SMTP` 能直接传二进制"**：正确做法是 `MIME` 是 `SMTP` 的**编码扩展**（把非 `ASCII` 数据编码成 7 位 `ASCII` 再交给 `SMTP`），真正传输邮件的协议仍是 `SMTP`（25）。
- ❌ **"`P2P` 中不存在服务器"**：正确做法是 `P2P` 通常仍有索引/追踪服务器（tracker）帮助节点互相发现，只是**数据不经过服务器**。
- ❌ **"`FTP` 的 `20` 是控制端口、`21` 是数据端口"**：正确做法是 **`21` 控制（整个会话期间保持）、`20` 数据（每传一次文件新建、传完即断）**。
- ❌ **"`HTTP` 无连接 = 不用 `TCP`"**：正确做法是 `HTTP` 用 `TCP` 80（`HTTPS` 443），"无连接/无状态"指不保存连接状态与客户信息，需要状态时靠 `Cookie` 补。
